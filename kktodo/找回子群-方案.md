# 找回已解散的子群（kkAgent reopen）方案

> **2026-11-13 修订（按 pm 评审和 KK 决定，以本节为准，下文第 2、3 步和「用法」作废）**
> KK 决定：群主自己记着会话 ID，由群主传，不由核心猜。
>
> ```
> kkAgent reopen -g <集群ID> --from <群主> --coder <coder 会话ID> [--tester <tester 会话ID>] --task <功能名> - <<'EOF'
> <这次要做什么>
> EOF
> ```
>
> - 不传 `--sub`。worktree 用 coder 会话记录里的工作目录（Transcript.readCwd），校验以下几点：
>   - 目录还在；
>   - 是群主仓库的 worktree（`git rev-parse --git-common-dir` 和群主仓库的一致）；
>   - 当前检出了一个分支，子群的 branch 就用它；
>   - 没有现存子群在用这个 worktree。
> - `--tester` 可以不传，不传就按 spawn 新建一个 tester。传了的话，它的工作目录必须和 coder 的一样，否则拒绝。
> - 会话按 ID 找（Transcript.find，coder 在选定的虚拟机里，tester 在物理机上）。分段文件的身份问题（评审第 1 条）就不涉及了：这里不按工作目录挑候选，Codex 用的是现有的 codexSessionFiles，已经按真实 ID 合并分段。
> - 再次找回（评审第 3 条）：dissolve 返回给群主的文字里直接给出带这次 coder / tester 会话 ID 的 reopen 命令，不依赖子群 ID。
> - 占用检查、入群说明、返回文字、ownerIntro 等其余部分按原方案。

## 背景

2026-11-13 14:40，集群「ifour小程序」的群主 owenr 想找子群 gbl49（19.2-R2，已解散）原来的 coder 验证真实配置。
命令行里没有找回子群的办法，它就直接调核心接口，建了一个**普通群** g32fn，再按会话 ID 把原 coder 拉了进去。
结果有两个问题：

- 普通群不挂在集群下面，在列表最上面，看着像子群乱了；
- 按会话 ID 拉进去的 coder 不是 tmux 托管的（每次投递都在后台续接一轮），用户在右边看不到终端。

KK 要求：给群主一条正规命令，在原集群下面找回子群，coder / tester 接着原来的会话，在 tmux 里运行。

## 用法

```
kkAgent reopen -g <集群ID> --from <群主名字> --sub <原子群ID> --task <功能名> - <<'EOF'
<这次要它们做什么>
EOF
```

`--sub` 是 spawn 时的原子群 ID，对应原来的分支 `kkagent/<原子群ID>` 和 worktree。

## 核心做法（Cluster.reopen）

1. **校验**：权限和 spawn 一样，必须是集群主群，`--from` 必须是这个集群的群主。功能名和说明都不能为空。
2. **找 worktree**：在群主仓库里执行 `git worktree list --porcelain`，找分支 `refs/heads/kkagent/<原子群ID>` 所在的目录。
   - 新旧两种目录布局（`.worktrees/<id>`、`-kkwt/<id>`）都能找到，也不需要新建表；
   - 分支或 worktree 已经被删掉就拒绝，说明「删不删由用户决定，已经删了没法找回」；
   - 已经有现存子群在用这个 worktree（groups.worktree 相同）就拒绝，告诉群主那个子群的 ID。
3. **找会话**：
   - coder 是虚拟机里工作目录等于这个 worktree 的 Claude 会话，取最近修改的一个（`Sessions.list(.claude, vm)`）。
     虚拟机的选法和 spawn 一样：群主在哪台虚拟机就用哪台；群主在物理机上时，只有一台虚拟机在运行才用它。
   - tester 是物理机上工作目录等于这个 worktree 的 Codex 会话，取最近修改的一个。
   - 找不到 coder 会话就拒绝（找回的意义就是接着原 coder）。找不到 tester 会话就按 spawn 的方式新建一个 tester。
4. **占用检查**：同一个会话不能被两个进程同时写。
   - coder 或 tester 会话已经是某个群的成员（repo.membersUsing）就拒绝，说明在哪个群、叫什么名字。
     比如 g32fn 还在用 gbl49 的 coder，就会被拒绝，并提示请用户先解散 g32fn。
   - 会话正在「会话」页里开着（还没结束的单独会话）也拒绝，提示请用户先在「会话」页销毁。
5. **建子群**：
   - `createGroup(name: task, parentId: 集群, owner, baseBranch: 群主仓库当前分支)`；
   - `setGroupWorktree` 设成原来的 worktree 和分支 `kkagent/<原子群ID>`，不新建 worktree、不新建分支；
   - 群主照抄它在主群里的成员行。coder 和 tester 用找到的会话 ID，tmux 托管，`headless: true`；
     tmux 名按新子群 ID 起（`kk-<新ID>-coder`）。
6. **入群说明**：原会话记得的还是旧群 ID，必须告诉它们新的群 ID 和发消息的命令。
   - **coder**：在 `subgroupBasics`（新群 ID、成员、命令、规则都在里面）后面加一段：「你之前在子群 <原ID> 里做过这个功能，子群解散后被群主找回；还在原来的 worktree 和分支。这次要做的是下面的需求。」需求就是群主写的说明。purpose 用 `.task`，收到就开工。
   - **tester 是接着原会话的**：同样的基本说明，加上「等 coder 找你，现在只回复已就位」。purpose 用 `.notice`，不用 bootstrap，因为会话已经有了。
   - **tester 是新建的**：完全按 spawn 的 testerIntro，purpose 用 `.bootstrap`。
   - 顺序和 spawn 一样，tester 的说明先排队。
7. **投递**：tmux 成员第一次投递时由 `ensureTmuxSession` 打开 tmux。Claude 的会话文件存在，所以用 `--resume`；Codex 用 `resume <ID>`。这部分是现有逻辑，不用改。
8. **返回给群主的文字**：新子群 ID、worktree、分支，coder / tester 是接着原会话还是新建的，以及发消息的命令。
   再加一句：以后再找回，仍然用原子群 ID `<原ID>`，因为分支名没变。

## 群主怎么知道有这条命令

- `ownerIntro` 加一条：「要找回已解散子群的 coder / tester，用 `kkAgent reopen`。**不要**自己调接口建普通群拉成员。」
- 已经在跑的群主收不到新的 `ownerIntro`。所以 `dissolve` 的返回文字里也写上找回命令，这个提示每次解散都会出现。
- CLI 的 `bin/kkAgent` 加 `reopen` 命令，usage 里也加上。

## 不做的

- 不新建「子群归档」表。worktree 靠分支找，会话靠工作目录找。
- 不自动处理 g32fn。它现在还在用，由用户或 owenr 决定什么时候解散。
- 不支持指定会话 ID 覆盖。按工作目录找到的最近一个就是原来的 coder / tester；以后真碰到选错的情况再说。

## 验证计划（测试核心 7799）

1. 在测试集群里 spawn 一个小子群，等 coder 和 tester 都起来，然后 dissolve。
2. reopen：
   - 新子群挂在集群下面（parent_id 对）；
   - coder 和 tester 的会话 ID 跟原来一样，tmux 命令带 `--resume` / `resume`；
   - 问 coder 之前做过什么，能答上来；
   - 在新群里能用新群 ID 发消息。
3. 拒绝场景：
   - `--sub` 不存在；
   - worktree 已经在现存子群里（连续 reopen 两次）；
   - coder 会话已经被一个普通群占用；
   - 会话在「会话」页开着；
   - 不是群主；
   - 不是集群。
4. 测完把测试群解散、关掉测试核心，确认没有残留的 tmux。
