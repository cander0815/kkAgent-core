# kkAgent 参考 OpenMausBot 的多 Agent 管理优化建议书

日期：2026-11-13  
适用对象：当前 Swift 原生版 kkAgent，重点是本地及虚拟机中的 Claude、Codex 会话和集群子群。  
状态：方案建议，供后续评审和实施使用；本文没有实施业务代码变更。

## 一 结论与优先级

建议在现有可靠投递和 worktree 隔离之上，补齐任务记录、结果回收和引擎适配。OpenMausBot 最有价值的地方，是把一次委派建模为有负责人、有完成条件、有结果去向的工作记录，而不是只保存聊天内容。

我们已经实现了按真实会话串行投递、忙时合并消息、未确认投递阻挡、授权等待识别、人工接入终端和子群 worktree。优化应复用这些能力。

| 顺序 | 建议 | 解决的问题 | 实施规模判断 |
| --- | --- | --- | --- |
| 1 | 任务记录与执行阶段 | 多个子群同时工作时，需要知道每项任务进展、等待对象和最终合并结果 | 中等，涉及模型、存储、接口、CLI 和界面 |
| 2 | 显式消息意图与结果回收 | 明确交办、咨询、通知，以及结果需要交给谁 | 中等，可依附任务记录分步实施 |
| 3 | 统一引擎适配接口 | 发送、状态、打断等能力分布在多条执行路径，扩展成本较高 | 中到较大，应先抽接口，再试验新协议 |
| 4 | 按机器控制启动并发 | 多个子群集中启动时，控制 CLI 和 MCP 初始化的资源竞争 | 小到中等，参数与收益需要实测 |
| 5 | 可配置角色模板 | 将职责、引擎、运行位置分开，支持不同团队组合 | 中等，依赖适配层和能力校验 |
| 后续 | 增量上下文、事件推送、空闲进程回收 | 进一步改善长会话成本、状态实时性和资源占用 | 按实际需求独立评估 |

这里的优先级是建设顺序，不代表发现了必须立即修复的故障。资源瓶颈、延迟改善和 token 节省尚需基于我们的运行数据验证。

### 2.3 两个需要明确的现状

第一，我们已经通过提示词减少无意义往返。K9 明确要求子群成员“只是知会、不需要你做什么时不回复”，代码注释也记录了来回确认的实际案例。因此第二项建议是把既有约定写进协议，方便核心处理和界面表达。

第二，tester 验收通过不代表集群任务完成。K8 已要求 coder 将代码合并回目标分支，报告最终 SHA，群主确认后再解散子群。K7 也明确要求 pass 先发给 coder。新的任务状态必须覆盖合并阶段。

## 三 建议一 增加任务记录与明确的执行阶段

### 3.1 参考设计与修改原因

参考 O1、O3、O5。OpenMausBot 的 Assignment 把一次工作从聊天里单独提取出来，可以查询负责人、父子关系、完成条件和结果。任务记录与发送给 agent 的文字是关联关系。

当前 K1、K10 的主要对象是群、成员、消息和投递。K2 用一个子群承载一个功能，已经有天然的任务边界，但任务阶段主要依赖聊天和 K8 的提示词约定。

当五个子群并行时，“成员空闲”无法说明它已经做完、正在等 tester，还是遇到问题后结束了一轮。“消息已送达”也只能证明消息送进了会话。增加任务记录后，界面和群主可以直接读取这些事实。

### 3.2 第一版范围

先保持“一个集群子群对应一个功能任务”。不开放子群继续递归拆分，不同时引入完整的通用任务树。普通群继续使用现有聊天方式。

建议新建任务表，字段如下。这是 kkAgent 的拟议模型，不是 OpenMausBot 字段的逐项复制。

| 字段 | 含义 | 作用 |
| --- | --- | --- |
| id | 任务 ID | 关联消息、验收与结果 |
| groupId | 执行子群 | 复用现有成员及 worktree |
| requesterMemberId | 委派者的成员记录 | 明确结果返回对象，避免仅用显示名称 |
| assigneeMemberId | 当前执行负责人 | 表示当前由谁处理 |
| title、brief、doneWhen | 标题、需求、完成条件 | 供执行与验收共同读取 |
| stage | 当前阶段 | 供核心和界面统一解释 |
| revision | 本次提审轮次 | 将验收结论对应到具体一轮工作 |
| submittedSha | 本轮送审的提交 | 记录 tester 验了哪份代码 |
| mergedSha | 最终合并提交 | 区分验收完成与交付完成 |
| resultMessageId | 结果消息 | 保留完整说明，避免复制多份正文 |
| blockedReason | 受阻原因 | 给群主或用户提供可处理的信息 |
| createdAt、updatedAt | 时间 | 排序和呈现最近进展 |

首版只需要当前集群与子群的两级关系；是否增加 parentTaskId 和依赖列表，等任务记录跑通后再决定。

### 3.3 阶段和证据

| 阶段 | 由什么动作进入 | 不能用什么替代 |
| --- | --- | --- |
| queued 待执行 | 任务创建、等待初始化或投递 | 创建了子群不等于已经开工 |
| working 编码中 | coder 显式开工，或已关联任务的开工证据被确认 | 任意终端输出不能单独证明这项任务开工 |
| reviewing 验收中 | coder 提审并提交本轮 revision 和 SHA | 发了一条普通消息不等于正式提审 |
| integrating 合并中 | tester 对本轮送审记录给出 pass | pass 不能直接写为 completed |
| completed 已完成 | coder 报告合并结果，核心验证目标分支包含报告的提交 | 一轮进程结束不能替代任务完成 |
| blocked 受阻 | 执行者明确报告问题，或现有打回上限规则触发 | 授权等待只影响可运行性，不自动断言业务受阻 |
| interrupted 待核对 | 核心重启打断了托管执行，暂时无法判定实际进度 | 重启不能直接清空任务或自动重做 |
| cancelled 已取消 | 用户或群主显式取消 | 移除一个成员不应自动宣称任务成功 |

正常循环是：待执行 → 编码 → 验收 → 合并 → 完成；验收 fail 回到编码，并进入下一轮提审。受阻和中断后的恢复由群主或用户明确选择，不通过“成员又变空闲”自动恢复业务阶段。

首版将“测试结果、文件改动”等写入结果说明，并记录提交 SHA。核心可以验证 git 中的提交关系；测试是否充分仍由 tester 和群主判断，不把一段模型总结包装成客观验证。

### 3.4 需要修改的位置

1. K1 增加任务与任务事件的接口模型；K10 增加任务、阶段事件及消息关联字段。
2. K2 在建立子群时登记任务。初始化失败时保留对应阶段与原因，避免界面只剩一个不知道是否已开工的群。
3. K7 和 `bin/kkAgent` 增加开工、提审、受阻、完成等显式操作；先供集群成员使用，不扩展全部聊天操作。
4. K8 提示词引用任务 ID 和当前 revision，说明每个阶段必须报告的内容。
5. K13 附近增加任务概要，保留原有交接消息。群列表显示“编码中、待验收、合并中、受阻”等业务阶段。

任务阶段更新、关联事件、需要发送的结果消息应在同一数据库事务中记录。K15 当前对每个 SQL 调用单独加锁，新增事务入口时应覆盖整个事务，并提供事务内操作方式；直接在现有非递归锁里调用再次加锁的方法会发生锁重入问题。这是实现新功能需要处理的事务边界，不要求改写全部存储层。

数据库事务无法同时包住 git worktree 创建和 CLI 启动。沿用现有分步创建方式，将任务先登记为待执行；某步失败则记录失败位置和可用的工作目录，让群主可以重试或取消。首版不为此引入通用工作流引擎，也不把初始化失败的任务误记为已经执行过。

### 3.5 子群解散与历史任务

任务完成后，K8 要求群主确认并解散子群。新增任务记录必须在这个动作之后仍可查询，至少保留任务标题、最终状态、提交 SHA 和完成报告。运行中的群与成员是执行资源，历史任务是交付记录，两者生命周期不同。

可以先在任务表保留完成报告快照和关键字段，再允许删除运行资源。不要让任务唯一的结果只依赖一条随后被连带删除的群消息。原始日志是否长期保留、是否提供任务归档界面，可以独立决定；首版至少保证完成摘要不会随解散消失。

### 3.6 一个完整例子

群主将“增加设置页”交给子群 A。任务创建时记为 queued；coder 开工后为 working。coder 在 revision 1 提交 SHA A1，任务进入 reviewing。tester 对 A1 给出 fail，任务回到 working；coder 修复后以 revision 2 提交 A2，tester 对 A2 给出 pass，任务进入 integrating。

随后其他功能先合并了主分支，coder 按现有规则同步并解决冲突。如果代码发生了需要重新验收的变化，按 K8 再发起一轮提审。最终 coder 报告合并 SHA A3，核心检查目标分支包含 A3，再记录 completed。群主确认并解散子群后，任务列表仍显示完成结果。

这里把“任务”“提审轮次”“最终合并结果”分别记录，既适配现有 coder 与 tester 流程，也让群主能看清返工和交付之间的关系。

### 3.7 成本与验收

主要成本是业务状态转换、CLI 约定、数据库升级和新界面。收益是进展可查询、结果有归属、验收和合并边界清楚；不能据此承诺模型会更快完成编码。

验收至少覆盖：创建子群后可查任务；tester pass 后显示合并中；最终 SHA 经验证后才显示完成；fail 关联正确提审轮次；授权等待与业务阶段分别展示；重启后保留任务和原因；旧群无需补造历史任务也能正常打开。

## 四 建议二 将消息意图和结果返回写进协议

### 4.1 参考设计与现有差异

参考 O2、O4、O11、O13。OpenMausBot 将“做事、咨询、通知”和“自动唤醒、等待查询、不回传”分开记录；需要回传的结果进入请求者的收件箱。

K9 已经用提示词要求成员避免互相确认。K7 仍主要根据 from、to、content 和 verdict 处理消息，核心无法直接查询这条消息是否期待结果。K4 的忙时合并解决了投递频率，但没有代替任务结果的关联。

### 4.2 建议的数据语义

| 意图 | 模型应如何处理 | 核心应记录什么 |
| --- | --- | --- |
| work 交办 | 执行并提供结果 | 任务 ID、负责人、完成条件和结果返回方式 |
| consult 咨询 | 回答问题，按咨询约定限制行动范围 | 问题、答案及请求者 |
| notify 通知 | 阅读即可，按约定无需确认 | 通知及送达事实，不建立待回复义务 |

咨询本身不是安全沙箱。如果只是写了“consult”并补充提示词，不能宣称已经阻止文件修改；确需只读执行时，应由对应引擎能力或工具范围落实，并说明当前支持情况。

结果方式先支持两种即可：`resume` 表示结果需要投回请求者；`none` 表示不产生自动回复义务。只有出现“群主主动查询统一收件箱”的需求时，再增加 `poll`。

### 4.3 为什么这样改

显式意图可以让核心按稳定字段组织待办和结果，不必从“好的”“完成了”“你看一下”等自然语言里猜工作关系。用户仍然可以自由聊天，正式交办和正式结果通过 CLI 或界面动作附带字段。

`notify` 不等于静默丢弃，也不等于禁止唤醒接收者。接收者可能仍需要运行一轮来读取通知；它的作用是明确不要求再次回复。是否只存档、是否投进模型，需要另行明确，不能仅靠这个字段承诺省掉一次模型调用。

### 4.4 结果回收流程

1. 创建交办记录时保存任务 ID、请求者及返回方式。
2. coder 或 tester 显式提交结果，核心持久化结果事件。
3. 对 `resume` 结果创建一条关联结果的回传消息，再交给现有 DeliveryQueue。
4. “已产生结果、已排队回传、已确认送达”分别记录。已写入未确认继续沿用现有处理，不能重复生成回传消息。
5. 同一请求者暂时忙碌时，复用 K4 已有的消息合并能力。以后若需要等全部子任务再汇总，可在任务层增加明确的汇总策略。

结果事件与回传消息建立唯一关联，避免核心轮询时重复创建同一结果的通知。首版可以利用数据库唯一键和事务实现，不必建立完整分布式消息系统。

### 4.5 暂不采用小模型过滤确认回复

O11 会先检查是否确实可能是纯确认，再调用小模型判断是否值得唤醒请求者；它有调用成本、等待时间和额外判断路径。

我们已有 K9 的提示词约定，下一步应先增加显式意图和结果关联。只有统计发现纯确认仍持续引发无效执行，才值得对比小模型过滤与规则处理。O11 的注释不能当成我们实际 token 消耗的测量结果。

### 4.6 验收重点

通知不会凭空新增待回复任务；咨询答案能关联原问题；正式结果关联原任务；重启不重复创建同一结果的回传消息；未确认送达不会标成“请求者已收到”；已有普通消息默认行为保持兼容。

## 五 建议三 统一引擎适配并逐步试验结构化执行

### 5.1 参考设计

O6 通过 ProviderAdapter 暴露能力和统一操作。O7 的两个驱动分别处理 Claude stream-json 和 Codex app-server，向上层提供统一事件，而不是要求上层理解每种 CLI 的原始协议。

### 5.2 当前需要澄清的执行路径

K4、K5、K12 表明，常驻 tmux 的集群成员普通消息走投递尝试流程；后台 Codex 的初始化可以通过 exec 获取会话 ID，再建立 tmux。不能根据 Delivery.swift 文件开头的历史概述，就把所有集群 Codex 运行理解成“每条消息 exec 一次”。

此外，已有桌面会话、Claude 中转和后台续接仍是不同路径。引擎类型、运行位置、会话是否由我们托管，都在影响执行方式。抽接口的价值是收拢这些差异，使任务层只关心操作与结果。

### 5.3 接口建议

先形成以下概念，不立即规定 Swift 的最终类型签名：

| 操作 | 约定 | 可复用位置 |
| --- | --- | --- |
| capabilities | 声明是否支持运行中追加消息、精确打断、审批响应和结构化事件 | K6、Readiness.swift 和现有执行路径 |
| ensureSession | 新建或恢复指定会话，返回真实会话身份 | K12 |
| send | 返回已接受、明确未发送或结果不确定，关联投递编号 | K4、K5 |
| interrupt | 请求打断并保留后续结算 | Interrupt.swift |
| observe | 提供状态与事件，并说明来源 | K6、Transcript.swift |
| closeManagedSession | 仅关闭本工具明确拥有的执行进程 | K12 的进程登记及关闭逻辑 |

不支持的能力应明确返回“不支持”，由上层展示可行操作。运行中追加消息如果结果不确定，应继续采用我们现有“不能盲目重发”的原则；O6 的 steer 也专门区分 refused 与 indeterminate。

### 5.4 两阶段落地

第一阶段只整理现有路径：把 tmux 投递、桌面 Codex 入队、Claude 中转和后台执行封装为不同适配实现，复用原有确认与状态逻辑，不同时改变用户交互。

第二阶段另建一条新托管会话路径，试验结构化协议。预期可更直接获得 turn、工具调用、审批请求和结束事件。原生协议事件可能减少屏幕解析依赖，但实际版本兼容性、会话恢复以及用户接管方式需要验证。

现有 tmux 成员能在 App 终端里直接交互，这是一项产品能力。改成后台结构化进程后，不能默认仍可用同样方式 attach。应先设计“查看执行、发送输入、处理审批、暂停或接管”的完整体验，再决定是否扩展使用范围。

### 5.5 为什么不直接替换全部运行方式

结构化驱动会增加协议请求匹配、事件生命周期、进程退出和恢复等维护工作。现有方案还包含我们需要的虚拟机执行和人工终端操作。先抽接口可以获得代码边界收益，同时保留验证成熟的路径。

是否切换由真实试验决定。记录初始化耗时、首次输出时间、投递确认耗时、恢复成功情况和人工接管体验，与原路径比较，不预先承诺速度提升比例。

## 六 建议四 按执行机器限制启动并发

### 6.1 参考位置与解决范围

参考 O8。OpenMausBot 给 Codex 初始化设置启动槽，多余启动请求进入等待；进程启动链推进到合适阶段后释放槽位，并处理取消等待和启动失败。

我们 K3 解决的是同一会话的串行投递，多个会话之间仍可并行。K2 连续创建多个子群时，会触发多个成员的初始化。是否已经造成机器资源瓶颈需要实测；启动调度是规模扩大时可以增加的控制能力。

### 6.2 建议流程

1. 按实际执行位置建立资源键，物理机和不同 VM 分开统计。
2. 只有需要创建新 CLI 执行进程时申请启动槽，向已经运行的会话投递不重复申请。
3. 获取启动槽之前不占用 SQLite 事务、不持有投递全局锁。
4. 到达启动就绪点、启动失败或操作取消时释放启动槽；用户取消排队可以及时移除请求。
5. 界面显示“等待启动资源”，与“对方正在工作”“等待授权”“投递未确认”区分。

启动槽不代表运行槽。一轮任务可能执行较长时间，如果整轮都占着启动槽，就变成限制任务并行度，失去原本的设计目的。

### 6.3 参数与验收

先提供可配置的每台机器启动并发数，通过单子群和多子群对比选择默认值。不直接套用 O8 按 CPU 核数计算的默认策略，因为我们的 CLI 分布在物理机和 VM，资源分配不同。

验收包括：同一资源键不超过设定启动数；不同 VM 独立排队；正常发送不受启动队列影响；取消和失败能释放槽位；没有后台等待占住全局锁。收益用初始化失败情况、启动耗时和资源峰值比较，接受“没有明显改善”的实测结果。

## 七 建议五 让角色模板与执行环境分别配置

### 7.1 参考设计与现状

O1、O6 体现了工作执行者、会话目的地和引擎能力的分离。O3 还会在任务真正调度前重新校验目标。

当前 K2 固定建立 coder 和 tester，并固定使用 Claude 编码、Codex 验收；源码还明确约束 coder 的 VM 运行位置和 tester 的物理机位置。这个默认组合有明确用途，首版应保留。

### 7.2 建议配置维度

| 维度 | 例子 | 约束来源 |
| --- | --- | --- |
| 职责 | 编码、验收、调研、方案分析 | 模板及完成条件 |
| 引擎 | Claude、Codex | 已实现的适配器及可用版本 |
| 模型 | 用户为该成员选择的模型 | 引擎实际支持情况 |
| 执行位置 | 指定 VM、物理机 | 当前产品约束、可访问目录和环境能力 |
| 交互方式 | tmux 托管、已有会话、结构化托管 | 适配器能力 |

先将现有组合做成默认模板，再考虑增加“单成员分析”等简单模板。角色名字可以配置，但创建前必须验证引擎、运行位置和交互方式确实兼容。遇到不支持的组合时说明具体原因，不静默改变位置或降低既有隔离要求。

### 7.3 为什么这样改

目前更换团队组合需要改创建流程和角色提示词。拆开配置后，常见组合可以由模板表达，创建流程负责实例化和能力校验，任务流程负责阶段与结果。

角色复用不等于复用同一个原生会话。不同功能默认仍使用独立子群和 worktree；群主跨子群复用同一个真实会话时，继续沿用 K3 的会话级串行队列。否则换成按角色或按子群排队，会破坏我们已经解决的同一会话并发投递问题。

### 7.4 成本与验收

可配置组合越多，需验证的路径越多。因此模板应少而明确，先验证现有默认模板，再增加一个实际需要的组合。验收包括默认组合行为一致、不支持组合给出原因、角色提示词不互相覆盖、主群和子群共享会话仍保持串行。

## 八 可保留的后续方向

### 8.1 任务摘要与增量上下文

O10 用 HandedState 记录指定原生会话已经接收的内容，并对未接收消息进行补充。它不是简单的“所有历史只留最后几条”，重要的队友结果有单独保留规则。

我们已经有会话续接和 K4 的排队消息合并，不能再把它们列为缺失能力。可以先规范完成报告：任务、提交、验证结果、未解决项，让群主收到可用摘要；只有确实增加跨线程上下文回放时，才需要引入“哪些内容已交给这个原生会话”的持久化游标。

若以后做摘要，仍应保留原始消息和报告链接，不能让摘要替代原始验收证据。窗口大小、压缩阈值和是否节省 token 都需要按实际引擎测量。

### 8.2 事件驱动的界面更新

O12 汇集引擎事件并合并文本增量。我们 K14 当前通过循环刷新界面，核心 K4 也有定时轮询与 hook 唤醒。

可以先在核心形成任务阶段变更事件，界面再按事件刷新相关群和任务。是否新增 SSE 或本地事件通道，取决于真实刷新延迟和数据量；暂时不必为少量群重写整个 HTTPServer。客户端推送通道和核心引擎事件总线是两个层次，不能把 O12 直接当作现成的界面推送实现。

### 8.3 空闲进程回收

O9 对保留的引擎进程设置空闲关闭策略，并利用会话身份恢复。其阈值和内存假设属于 OpenMausBot 的环境。

我们的 tmux 同时支持人工接入，进程空闲也可能是用户准备继续输入。只有后续引入了明确归核心拥有的后台结构化进程，才适合优先评估自动回收。现有终端会话先保持用户可控，不根据“长时间没输出”直接结束。

## 九 暂不照搬的设计及原因

| 设计 | 参考位置 | 暂不采用的原因 |
| --- | --- | --- |
| 任意多层递归委派 | O1、O14 | 当前主群加功能子群已经能承载主要流程；递归会增加取消传播、结果回收和生命周期复杂度 |
| 多维预算和超时自动结束整棵任务树 | O14、runtime/runtime.ts | 当前已有验收打回上限和人工介入；新增停止条件会改变任务行为，应由实际循环或停滞问题驱动 |
| 重启后自动重新执行未完成任务 | runtime/runtime.ts 的恢复分支 | 任务可能已经改文件或执行了外部动作；继续沿用 K11 的中断通知，再由群主判断恢复方式 |
| 用小模型判断每次回复是否值得唤醒 | O11 | 先完善显式意图，减少额外调用和判断分支 |
| 全量引入云端团队、账号体系和外部连接能力 | 参考仓库其他模块 | 当前目标是本地多 agent 管理，这些模块会显著扩大产品和维护范围 |
| 因理论上可能出错而补充大量兜底 | 不对应单一模块 | 先验证触发条件和实际影响；低概率假设单独讨论，不作为本次必须修复项 |

这几项是范围取舍。后续若有具体案例，应说明触发场景、发生频率、影响以及实现成本，再决定是否增加对应机制。

## 十 分步实施与验收安排

### 第一阶段 建立可查询的任务进度

范围：建议一。先支持一个子群一个任务，阶段包括验收和合并，界面保留聊天入口。

交付：任务模型和迁移、任务动作接口、CLI 支持、任务概要、明确的阶段转换及重启处理。

重点验证：正常交付、验收打回、合并受阻、授权等待、重启中断。测试围绕业务阶段与真实数据库事务，不为了文档、纯文案或低影响界面改动新增镜像测试。

### 第二阶段 建立结果回收约定

范围：建议二。对集群正式交办和结果增加结构化关联，普通聊天保持自由。

交付：意图字段、结果关联、一次结果对应一次回传、群主读取任务汇总的能力。

重点验证：多个子群同时回报、群主忙碌时合并处理、重启后不重复创建回传、未确认状态不误报已收到。对比正式任务中无效确认消息的数量，再判断是否需要更多优化。

### 第三阶段 整理适配层并试验一条新路径

范围：建议三。先封装现有发送和状态接口，再选择一类新托管会话做结构化驱动试验。

交付：能力声明、统一操作与事件、原路径验证、试验路径的用户交互方案。

重点验证：会话身份一致、准确恢复、中断结算、审批交互、用户接入体验，以及原有 tmux 可靠投递没有退化。试验没有体现收益时，可以只保留适配接口整理。

### 第四阶段 按运行数据增加资源调度和模板

范围：建议四、建议五。启动调度在第三阶段前也能独立实施，但资源槽必须挂在实际创建进程的位置。

交付：按机器排队、配置和状态展示；默认团队模板及一个确有需求的新组合。

重点验证：并发启动限制、资源释放、不同 VM 的队列隔离、模板组合能力与工作目录约束。

## 十一 需要通过实际运行回答的问题

1. 目前通常同时运行多少个子群？每台 VM 实际分配多少 CPU 和内存？这些数据决定启动调度的必要性和默认值。
2. 多 agent 管理的主要困难是看不清进展、无效消息过多、启动太慢，还是经常要人工接管？不同问题决定后续阶段是否提前。
3. 结构化托管会话如何满足用户直接操作的需求？需要先做可用原型，再决定替代范围。
4. 首版完成验证需要检查哪些仓库条件？建议最小从目标分支包含报告 SHA 开始；测试结论和代码验收继续保留 tester 的报告。
5. 是否需要一个子群里连续处理多个独立任务？当前建议先保持一个功能任务，避免提前引入通用任务调度器。

这些问题不影响先评审任务记录与结果回收模型。它们用于确定实施参数和扩展范围，不应通过增加猜测性的防御逻辑替代实际验证。
