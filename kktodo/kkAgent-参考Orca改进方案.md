> 要解决的两件事：
> 1. 集群里的 coder / tester 常驻在 tmux 里，用户要去外部终端 `tmux attach`、还要记住 `Ctrl-b d` 才能退出，用起来不方便；
> 2. 往 tmux 里投递消息比较「盲」：贴进去、固定等 0.5 秒、按回车，就算送达。

## 一、结论先说

| 问题 | 做法 |
|---|---|
| 终端不方便 | **后台继续用 tmux**（会话常驻 tmux 已经做好了），在 App 的成员详情里嵌一个 SwiftTerm 终端，里面跑 `tmux attach`。不照 Orca 重写终端守护进程 |
| 对方正忙 | **（KK 提的）对方在干活时，消息先存在核心里，等它空闲了再合并成一条送进去。** 用 hook 判断忙闲（tester、桌面端 Codex 用会话记录判断）。这样每次投递时对方的输入框都是空闲的，送达确认也最准 |
| 投递太盲 | 给 tmux 里的 coder（Claude）装状态 hook；投递改成「核对会话没换过 → 确认空闲、没有授权框和别人的草稿 → 贴 → 确认贴完整了 → 回车 → 用投递编号确认是这一条开工了」。每走一步都存进数据库，确认不了就记「**已写入未确认**」，**不当成送达，也不重贴** |
| 卡在授权框 | 识别出来，通知群主一次，等授权框消失再继续；**绝不替用户授权、回车或重贴** |

分五步做（hook → 忙时先存着 → 投递流程 → 授权框 → 嵌终端），每步真实跑通、给 KK 看结果后再做下一步。

## 二、Orca 是怎么做的（只摘相关部分）

### 1. 终端怎么显示、怎么常驻

- 单独的终端守护进程（`src/main/daemon/`）用 `node-pty` 持有所有终端，界面用 `xterm.js` 通过本地 socket 接上去。界面关掉、重启不影响 agent。
- 守护进程里跑一个不显示的终端模拟器（`@xterm/headless`），随时能拿屏幕文字、恢复历史画面。
- 等于自己写了一个 tmux，代价很大：`src/main/daemon/AGENTS.md` 记录了光是「socket 文件归谁」这一个问题就评审了 7 轮、出过 23 个缺陷。**kkAgent 不走这条路。**

### 2. 状态从哪来

- 主要靠 hook，每个事件用 curl 报给本机服务（`src/main/claude/claude-managed-hook-events.ts`、`src/main/agent-hooks/README.md`）。
- OSC 7501（agent 把状态写进终端输出）只做兜底，规则是「hook 优先，OSC 补空缺」，按来源分优先级和新鲜度，不是几个来源抢着改同一个状态。kkAgent 中间隔着 tmux，现在不用；以后可以研究 tmux 的 `pipe-pane` 能不能拿到原始输出（要验证查询和应答能不能对上、输出属于谁）。
- hook 上报做得很可靠（`claude/hook-script.ts`、`agent-hooks/installation/scripts/hook-stdin-contract.ts`）：本地落盘缓存（spool）、每次启动一个专属令牌、目录权限 700 / 文件权限 600，核心重启期间的事件也不会丢。
- 按实际启动的那台机器探测 Claude 版本，决定装哪些 hook 事件（`claude-hook-event-versions.ts`，比如 `PostToolBatch` 要 2.1.118 起才有）。

### 3. 怎么给 Claude 发一条消息

主流程 `src/main/runtime/terminal/input/terminal-agent-prompt.ts`：

| 步骤 | 做什么 | 原因 |
|---|---|---|
| ① 认准对象 | 核对终端里还是原来那个进程（进程代次） | 防止发给重启后的新进程 |
| ② 先看授权框 | 卡在授权框上就不写，等它消失，不设超时；等待放在单个终端的写入队列之外 | 否则文字会被当成对授权框的回答 |
| ③ 包装内容 | `ESC` 换成 `␛`，换行统一成 `\r`，括号粘贴包起来 | 防止文字里的控制字符提前结束粘贴、执行后半段 |
| ④ 等界面画完 | 至少等够按字节数估算的写入时间；之后看到光标重新出现再安静 1.5 秒，最多 8 秒；原来输入框是空的，就以输入框精确显示出整段内容、并持续 300ms 为准，可以提前结束 | 太早回车，内容还没进输入框 |
| ⑤ 单独按回车 | 回车和粘贴分两次写 | 粘贴结束符和回车放一起，Claude 可能把草稿留着不发 |
| ⑥ 补回车 | 一般情况下，要输入框里正好是自己贴的那段才补；但输入框已就绪的分支里有一次「不看就按」的回车 | 本项目更保守：只补一次，并且必须能证明输入框里是这次的内容 |
| ⑦ 回执分两层 | 可靠投递分支（`acceptQueued` / `requestId`）先回「输入已接受」，确认这次请求对应的开工后才加上「已开工」；这个分支**明确不把新输出当证据**（`allowOutputEvidence: false`）；`agent-prompt-request-correlation.ts` 保证同一次开工不会被两条请求同时认领 | 「对方忙的时候有新输出也算送达」只是老的观察办法，不是 Orca 可靠投递的标准 |

另外两处细节（pm 核对源码时找到的）：

- **授权什么时候算解除**：`src/shared/agent-hook-listener/claude-settled-permission-requests.ts` 只认「同一个主体（主 agent 或某个子 agent）、并且 `PostToolBatch` 的 `tool_calls` 里列出了正在等待的那个 `tool_use_id`」；`server-claude-status-rules.ts` 还会从匹配的 `PreToolUse` 补上 `PermissionRequest` 缺的工具 ID，防止旧的批次结束事件把新的授权等待清掉。
- **每次写入前都刷新状态**：`terminal-agent-prompt-submit.ts` 每次写之前先调 `refreshRestoredWait`，Orca 重启后不会盲目往一个可能还卡着授权框的终端里写。

## 三、本项目现状

| 文件 | 现在的做法 |
|---|---|
| `mac/Sources/Core/Tmux.swift` | `paste` = `load-buffer` + `paste-buffer -p` + 固定等 0.5 秒 + `send-keys Enter`；`exists` 只按会话名判断；`waitReady` 截屏找 `❯`，顺便按掉信任框 |
| `mac/Sources/Core/Delivery.swift` | 按会话分的串行队列。`deliver` 在 `send` 之前就把要合并的消息定死了；tmux 成员走 `ensureTmuxSession` + `Tmux.paste` |
| `mac/Sources/Core/Repository.swift` | `failUnfinishedDeliveries`：核心重启时把所有「投递中」记为「核心重启，投递中断」 |
| `mac/Sources/Core/Relay.swift` | 已经有从虚拟机里调核心接口的办法：经默认网关访问，Host 头写 `127.0.0.1:7788` |
| `mac/Sources/Core/HTTPServer.swift` | 只监听 `127.0.0.1` |
| `mac/Sources/App/GroupChat/MemberInspector.swift` | tmux 成员只显示会话名和「复制接入命令」 |
| `mac/scripts/build.sh` | 直接用 `swiftc -O` 编译 |

本机环境：tmux 3.6b，Claude Code 2.1.308，一台 ubx 虚拟机（hvf）。

评审中纠正过的两个事实：

- **`paste-buffer -p` 不保证一次写完**（pm 核对了 tmux 3.6b 的 `cmd-paste-buffer.c`）：只有终端开启了括号粘贴模式才加边界（Claude 会开启），而且内容会分几次写出去。所以回车前**必须在屏幕上确认粘贴完整进了输入框**。
- **虚拟机能连上核心**：虽然核心只监听 `127.0.0.1`，但 coder 已经实测，在虚拟机里经默认网关 `<网关地址>:7788`、Host 头写 `127.0.0.1:7788` 访问 `/api/health`，返回正常。这一条**依赖 ubx 的网络转发**，换虚拟化方式或网络模式要重新验证。

## 四、改动方案

### 第 1 步：给 tmux 里的 coder 装状态 hook

**hook 脚本**（核心启动时写到数据目录，比如 `~/.kkagent/hooks/status-hook.sh`；数据目录在 `/Users` 下，虚拟机里同一路径能看到）

- **不丢弃 stdin**：从事件 JSON 里取出需要的字段上传，同时带上成员 id 和**启动编号 launchId**（每次新建 tmux 会话生成一个）。
- 上传的字段：`session_id`、`hook_event_name`、`agent_id`、`agent_type`、`tool_name`、`tool_use_id`、工具输入的简短摘要、`UserPromptSubmit` 的 prompt 第一行和全文摘要、`PostToolBatch` 的 `tool_calls` 里的 `tool_use_id` 列表。
- `PermissionRequest` 单独输出 `{}`，其余事件**不往 stdout 打印任何东西**（`UserPromptSubmit` 的 stdout 会被加进上下文）。
- curl 设连接超时和总超时、`--noproxy '*'`、stderr 丢掉；核心连不上也 `exit 0`，不能影响 Claude 本身。
- 物理机连 `127.0.0.1:7788`，虚拟机沿用 `Relay.swift` 的网关办法。
- **身份校验**：launchId 用随机生成的长字符串，同时当作这次启动的专属令牌。核心收到事件时核对成员、session_id、launchId 三者都对得上才认；Host 头只用来挡网页，不算身份认证。设置文件所在目录权限设 700，文件设 600。

**挂载方式**：每个 tmux coder 生成一份只给它用的设置文件，启动时加 `--settings <文件>`。

**版本探测**：建 tmux 会话前，在**实际要跑的那台机器**上执行一次 `claude --version`（虚拟机里的版本不能拿物理机的代替）。只装这个版本认识的事件；低于 2.1.118（没有 `PostToolBatch`）时，授权只靠 `Stop` / `UserPromptSubmit` 解除；探测失败或挂不上 hook 时，明确降级为「状态未知」，界面显示原因。

**核心重启期间丢掉的事件**：首版不做 Orca 那样的本地 spool，改为核心启动后先读会话记录补齐事实（最后一条是用户消息还是 assistant 的结束），再用截屏核对。补回来的历史只用来恢复「做没做完」，不能用旧的 working / Stop 覆盖当前的授权等待。事件按 (launchId, 事件名, 时间戳/tool_use_id) 去重。

**核心**：新增 `POST /api/members/:id/hook`，在内存里维护每个成员的状态（新文件，比如 `Core/AgentStatus.swift`）。接收 hook 不经过投递队列，也不占数据库锁。

| 状态 | 怎么进入 |
|---|---|
| `unknown` | 核心刚启动、tmux 会话刚建好、或者收到的事件对不上当前的 launchId / session_id |
| `working` | 主 agent 的 `UserPromptSubmit` |
| `waitingPermission` | 任意主体（**包括子 agent**）的 `PermissionRequest`。记下 `(agent_id, tool_use_id)`；没带 `tool_use_id` 就从同一主体最近一次匹配的 `PreToolUse` 补 |
| `idle` | 主 agent 的 `Stop` / `StopFailure`，并且没有未解除的授权等待 |

规则：

- **授权解除**：只有同一主体的 `PostToolBatch`、并且它的 `tool_calls` 里列出了正在等待的那个 `tool_use_id`，才解除那一条等待；所有等待都解除了才离开 `waitingPermission`。主 agent 的 `Stop` / `UserPromptSubmit` 只能清掉**主 agent 自己的**等待，**不能删除子 agent 还没解除的授权**（主 agent 回复完了，子 agent 的授权框可能还占着终端；Orca 的 `server-claude-status-rules.ts` 也专门保留这种等待）。子 agent 的授权只在精确匹配的批次结束、该子 agent 结束（`SubagentStop`），或者截屏证明授权框确实已经不在时才清理。
- **子 agent**：子 agent 的普通事件不改变主 agent 的「干活中 / 空闲」，但它的授权框会占住这个终端，所以照样要挡住写入。
- **对不上的事件一律忽略**：launchId 或 session_id 不是当前这个会话的，不改状态，防止旧事件解除新的等待。
- 「进程已退出」不放进状态表，直接查 tmux 的 `pane_dead`；「启动中」由 `ensureTmuxSession` 自己管。
- `SessionStart` 只说明会话起来了，**不能当作可以粘贴的依据**。
- 群详情 `GET /api/groups/:id` 的 `MemberState` 带上这个状态，方便验证，界面以后也能用。

**【待实测】**

1. `--settings` 里的 hook 会不会和用户自己的 `~/.claude/settings.json`、项目级 hook **一起生效**（而不是覆盖）。
2. 2.1.308 里 `PermissionRequest` 输出 `{}` 和不输出的行为分别是什么，确认输出 `{}` 时授权框照常弹出。
3. `PostToolBatch` 在授权被通过 / 被拒绝 / 被取消、以及多个工具同时跑时，`tool_calls` 里是否都列出了对应的 `tool_use_id`。
4. 对方正在干活时贴进去的消息，`UserPromptSubmit` 在什么时候触发。

**实测结果（2026-11-12，宿主机 Claude Code 2.1.308，tmux 里交互运行）**：

1. `--settings` 传入的 hook 和项目级 `.claude/settings.json` 里的 hook **都会触发**，是合并生效的。注意 `/hooks` 菜单里**不显示** `--settings` 来源的 hook，不能靠菜单判断。
2. `PermissionRequest` 输出 `{}` 时，授权框照常弹出。
3. `PermissionRequest` **不带 `tool_use_id`**，要从前一个 `PreToolUse` 补（工具名和参数相同）。
4. **批准授权** → 触发 `PostToolBatch`，`tool_calls` 里列出对应的 `tool_use_id` → 再触发 `Stop`。
5. **拒绝授权** → **一个 hook 都不触发**（没有 `PostToolBatch`，也没有 `Stop`），这一轮直接以「Interrupted」结束。会话记录里会写：这个 `tool_use_id` 的 `tool_result`（内容是被拒绝），然后是一条 `type: user`、内容为 `[Request interrupted by user for tool use]` 的记录。**所以「等授权」状态必须靠会话记录兜底解除**：看到等待中的 `tool_use_id` 出现了 `tool_result`，就解除。
6. **主 agent 的事件不带 `agent_id`**，子 agent 的带（`SubagentStop` 实测有 `agent_id`）。`Stop` 之后有时还会跟一个内部子 agent 的 `SubagentStop`，要忽略。
7. `UserPromptSubmit` 带 `prompt` 原文和 `prompt_id`；之后同一轮的所有事件都带同一个 `prompt_id`，可以用来区分回合。
8. （第 6 步相关）在 Claude 还在思考、没开始输出时按 Esc：**不触发任何 hook，会话记录里也没有打断标记**，而且 Claude **把原来的提示词放回了输入框**。所以打断之后输入框里可能残留着上一条提示词，第 6 步合并投递前必须处理。

**第 1 步实现时的补充发现（已处理）**：

9. **批准授权也会在会话记录里写 `tool_result`**，所以 `tool_result` 只能说明「授权框没了」。只有主线最后是打断标记、之后没有新回复时，才能认定这一轮结束。
10. **启动令牌只放在内存里不够**：核心重启后 tmux 里的 Claude 还活着，它发来的事件会因为令牌对不上被一直忽略。所以令牌要存进数据库（`members.launch_id`），核心启动时恢复登记。
11. **tmux 会话不在时，状态一律返回 `unknown`**，否则旧进程留下的授权等待会一直显示。
12. **信任框的时序问题**（原有代码）：Claude 启动得快时，按「向下」可能还没生效就按了回车，选中默认的「No, exit」，Claude 直接退出。已改成每次先看选中的是哪一项，选中「Yes」才按回车。
13. （第 3 步相关）Claude 会在空输入框里显示**建议文字**（比如「推送到远端」），截屏判断「输入框里有没有别人的草稿」时要排除这种情况。
14. 核心用 `--resume` 重开 coder 后，hook 上报的 `session_id` 和原来一致，事件照常被认。

**验证**：真起一个子群（coder 在虚拟机里），curl 群详情，看状态随 coder 干活、停下、弹授权框、授权后而变化；核心重启后状态先是 `unknown`。

### 第 2 步：对方忙就先存着，空闲了再合并投递（KK 提的）

**规则**：所有「交出去就算完成」的投递方式（tmux 里的 coder / tester、桌面端 Codex 的 `codex queue`、经中转会话发给开着窗口的 Claude），**只在对方空闲时才投**。对方在干活或卡在授权框上，消息就留在核心队列里（状态保持 `pending`），等它空闲了，把攒下的消息合并成一条一次送进去。

**怎么判断忙闲**

**忙闲只有三种结果：空闲 / 忙 / 未知。未知一律按「不投」处理**，绝不当成空闲。

| 成员 | 依据 |
|---|---|
| tmux 里的 coder（Claude） | 第 1 步的 hook 状态：只有 `idle` 才算空闲；`unknown` 时读会话记录 + 截屏，能确认回合已结束、并且画面上没有授权框，才转成空闲 |
| tmux 里的 tester、桌面端 Codex | 会话记录，但**不能直接用现在的 `Transcript.isCodexBusy`**：它只读最后 200KB，判断不出来时默认「空闲」。一轮输出超过 200KB、`task_started` 落在窗口外，就会误判成空闲；文件读不到时也是空闲。改成**按文件增量维护**：记住读到的位置，逐行跟踪成对的 `task_started` / `task_complete` / `turn_aborted` 和会话身份；第一次从头扫完整个文件来重建；读取失败或重建不了，就是「未知」 |
| 开着窗口的 Claude（经中转会话发送） | `claudeLiveStatus` 明确是 `idle` 才算空闲，空值或不认识的值算「未知」 |
| 后台续接的 Claude / Codex（`-p` / `exec`） | 不变：投递本来就要等这一轮跑完，已经会合并 |

**会话级占用：防止同一个会话被同时投两次**

- 多个群的成员可能指向同一个会话；`Stop` hook 和定时检查也可能同时触发。所以认领必须**按真实会话**做，并且是原子的。做法是复用现有的「按会话分的串行投递队列」（`Delivery.swift` 的 `QueueKey.session`，几个群里指向同一会话的成员已经共用一条队列）：认领只在这条队列里进行，在里面检查「空闲」，再把这一会话标记为「有投递在途」，并记下 attemptId。
- 这个会话**有投递在途、或者有「已写入未确认」的 attempt 时，不再派新的 attempt**。
  - **送达确认后**：要等观察到**这个 attempt 对应的**「开工」或「已结束」事实之后，才解除在途标记。不能确认刚到、忙闲状态还没刷新，就按旧的「空闲」再派一次。
  - **一直确认不了**：**不会因为对方又跑完一轮就自动解除**。那一轮可能是人手动输入的、或者更早排着的消息，没确认的内容可能还留在输入框或者对方的队列里。处理顺序是：先用原来的编号和摘要补确认；再看输入框里是不是还留着没提交的草稿，留着就交给用户处理；证据不够时通知群主和用户，由**人明确选择「解除并继续」**。
  - **人工解除只解除调度上的阻挡**：旧的 attempt 仍然保持「已写入未确认」，绝不改成送达，也绝不自动重投。界面上给这种 attempt 一个「解除并继续」按钮。
- `codex queue` / 中转会话返回之后，到会话记录或 hook 显示「干活中」之间有一段空档。在途标记正好覆盖这段空档，空档期间不会再派一次。
- `Stop` hook 和定时检查**只负责唤醒**：往这条队列里放一个「看看有没有排队消息」的任务。重复唤醒没关系，任务开头会检查有没有排队消息、有没有在途投递，不会各自建一次投递。
- 认领之后、真正写入之前，**再复核一次忙闲和画面上有没有弹框**：人随时可能先在终端里开工。

**什么时候再投**

- coder 的 `Stop` / `StopFailure`、子 agent 的授权解除、「未知」经核对变成空闲、面板上从「暂停」恢复，都会立即唤醒一次；
- 再加一个定时检查（比如每 3 秒）兜底，查「有排队消息的会话」是否空闲了。漏掉的唤醒都由它补上，没有 hook 的成员也靠它；
- **等待不占投递队列**：对方忙时直接返回，消息保持 `pending`，不在队列里 sleep。所以「等待堵住队列、不能取消、核心退出卡住」都不会发生。成员被移出、子群解散时，排队的投递记录照旧删掉。
- 每次真正开始投递时才取「这个成员当前所有排队消息」合并，所以等待期间新来的消息都会并进去（顺带修掉了现在 `deliver` 在 `send` 前就定死合并范围的问题）。

**好处**

- 投递时对方大概率是空闲的，「忙时插进去的消息确认不了」的情况**大大减少**。但人可能抢先在终端里开工、hook 也可能晚到，所以第 3 步的「已写入未确认」处理**照样保留**。
- 桌面端 Codex 的消息不会再一条条堆在 Codex 自己的队列里（就是 KK 截图里 pm 堆了三条的情况）。
- 对方一轮只处理一次合并后的最新内容。

**代价**：对方干活中途收不到消息，比如 tester 发现方向不对想让 coder 马上停，要等 coder 这一轮做完。见第七节，需要 KK 决定要不要给「用户 / 群主的消息」开插队的口子。

### 第 3 步：改写 tmux 投递流程（确定对方空闲之后）

**投递编号**：`Prompts.delivered` 的第一行加一个**专门的编号行** `[kk#<attemptId>]`。一次投递（可能合并了好几条消息）是一个 attempt，数据库里记下 attempt → 包含哪些 deliveryId、全文摘要、走到了哪一步、凭什么确认的。编号只是给模型看的一行，不往群聊正文里塞技术字段。

**写入检查点（存数据库）**：`pending → preparing → write_started → input_accepted → confirmed`

- `write_started` 在**第一个可能进入终端的字节之前**落库；
- 崩溃或核心重启后：停在 `preparing` 及以前的，可以安全重投；停在 `write_started` / `input_accepted` 的，一律记为「已写入未确认」，**不能因为没走到 `input_accepted` 就认定没有副作用**；
- 现在的 `Tmux.paste` 把「载入、粘贴、等待、回车」包成一个会抛错的函数，出错时分不清是「还没贴」「贴了没回车」还是「回车已到、回执丢了」。要拆成几个独立的步骤，每步回报自己走到了哪；
- 会话代次变化同理：第一次写入之前发现变了，可以记失败；写入之后才发现变了，记「已写入未确认」，不能一律记失败。否则人看到失败去重投，会造成重复。
- **阶段只进不退**：回车后 hook 可能比 `send-keys` 返回得还快，先把 attempt 确认了，之后记 `input_accepted` 或超时处理时不能把它降回去。所以每次更新都写成「同一个 attempt、并且当前阶段比新阶段靠前才更新」（SQL 里用 `WHERE attempt_id = ? AND stage < ?`）。
- **先登记、再写入**：开始写入之前就把这次的 attemptId 和全文摘要登记好，hook 回执随时到都能认领。
- **重启后也能补确认**：核心重启后，迟到的 hook 或会话记录只要 attemptId 和完整摘要都对得上，照样可以把「已写入未确认」转成 `delivered`。
- **这套规则对所有「交出去就算完成」的投递方式都适用**，不只是 tmux：`codex queue`、中转会话的调用一旦开始执行，就算「已写入」。之后出错或超时都记「已写入未确认」，不能记失败后让人去重投。

**流程**：

1. **认准会话**：tmux 会话建好时记下 `pane_id`（`%N`）、`pane_pid` 和 launchId；粘贴前、回车前各核对一次。
2. **确认可以写入**：状态是 `idle`（第 2 步已经保证）；再截屏只看**输入框那一块**：里面有别人打的字、或者开着选择菜单、或者有弹框，就不贴，消息继续排队。
3. **记 `write_started`**，**转义 + 粘贴**：文字里的 `\u{1b}` 换成 `␛`，然后 `load-buffer` + `paste-buffer -p`。
4. **确认粘贴完整**：只看输入框那一块。输入框原来是空的，所以以「输入框精确显示出这次内容、连续 300ms 不变」为准；长内容会折叠成 `[Pasted text … +N lines]`，行数一致只是**辅助判断**（行数相同不代表内容相同）。8 秒是可以调的观察上限，超时不是送达证据。**确认不了就不按回车**，记「已写入未确认」。
5. **再核对一次会话和输入框**（防止用户在粘贴和回车之间打了字），然后 `send-keys Enter`，记 `input_accepted`。
6. **确认送达**（记 `confirmed`）：
   - 主依据：`UserPromptSubmit` 的 prompt **第一行完整解析出编号**，等于当前这次未确认的 attemptId，launchId 一致，**规范化后的全文摘要也一致**，才算送达。只是「prompt 里出现了这个编号」不算，因为引用旧消息、或者有人粘贴了旧编号都可能误中；
   - 一次开工只能认领给一个 attempt（同 Orca 的 `agent-prompt-request-correlation.ts`）；
   - 补充依据：会话记录里新增的用户消息，同样按编号行和全文摘要比对；
   - 下面这些**都不能证明送达**：开工计数增加（可能是人手动输入的）、出现新输出、输入框清空。
7. **补回车**：最多一次，而且同时满足这几条才补：能确切证明输入框里就是这次的内容、pane 和代次没变、没有人在操作、没有弹框。证明不了就不补。
8. **结果**：确认送达 → `delivered`；写入前中止 → `failed`（可以重投）；写入了但确认不了 → `written_unconfirmed`，**不重投、不重贴**，之后迟到的 hook 或会话记录能确认，再转成 `delivered`。

**核心重启**：`failUnfinishedDeliveries` 按检查点区分。写入前的（`preparing` 及以前）**改回 `pending`，由恢复流程重新排队**，不能沿用现在「先标失败、再只补投排队中的」的做法，那样它们会被漏掉。已写入的单独记为「已写入未确认」，并通知群主。`afterTurn` 也按这几种结果调整。

**第 3 步实现时的实测发现（2026-11-12，Claude Code 2.1.322 / codex-cli 0.167）**：

1. Claude 空输入框里的**建议文字是变暗的**（`ESC[2m`），用 `capture-pane -e` 截屏、去掉变暗的部分，剩下的才是真实草稿。
2. Claude 的长粘贴占位 `[Pasted text #N +K lines]` 里的 K 是**换行的个数**（5 行显示 +4），不是行数。5 行左右的短消息也会折叠成占位。
3. Claude 把粘贴的内容**包一层**再交给模型：`<pasted_content id="xxxx">\n原文\n</pasted_content id="xxxx">`。UserPromptSubmit 的 prompt 和会话记录里都是这样，比对编号前要先拆掉这一层（只在整条消息正好就是一个块时才拆）。
4. Codex 0.167 的会话记录里**没有 `user_message` 事件**，用户消息记成 `response_item`、类型 `message`、角色 `user`，文字在 `input_text` 里。
5. Codex 的输入框以 `›` 开头，段落之间可以有空行；屏幕最下面是状态栏，和输入框隔一个空行。
6. `Ctrl-U` 在 Claude 里只删当前一行，多行草稿删不干净（我们本来就不动别人的草稿）。
7. 偶发一次：tester 的 tmux 会话刚启动 9 秒时贴进去的消息，Codex 自己提交了（没按回车）。没能复现。系统按设计记成「已写入未确认」、没有重贴，随后从会话记录补确认成「已送达」。

**tester（Codex）**：这次不装 hook（要改 Codex 的全局配置）。用同一套会话核对、输入框检查、转义、粘贴确认、检查点，用会话记录里的编号确认送达。

### 第 4 步：授权框的处理

- 有了第 2 步，等授权就是「对方不空闲」的一种，消息自然留在核心队列里，**不需要单独的等待逻辑**。
- **通知**：同一个授权周期只在子群里发一次系统消息（`kind = alert`），说明是谁（主 agent 还是子 agent）、卡在什么工具上；等太久可以再提醒一次，阈值可以配置。
- **绝不**：自动授权、自动按回车、自动重贴。

### 第 2~4 步的验证

真跑 spawn，覆盖下面每一种情况，确认只开工一次、不丢、不重复，状态和群聊里的显示对得上：

- 短消息、几千字的长消息；
- coder 干活中途连发几条：确认先存着，`Stop` 后合并成一条送进去；
- 桌面端 Codex 正在跑一轮时连发几条：确认合并后才交进去；
- 开头相同、行数相同但正文不同的两条消息；
- 重复的编号；
- 子 agent 触发授权；
- 旧的批次结束事件晚到；
- 你正在终端里打字时，正好要投递；
- 虚拟机断网；
- 核心在粘贴和回车之间重启；
- 同名的 tmux 会话被重建；
- 同一个会话在两个群里，两边同时来消息、`Stop` 和定时检查同时唤醒：确认只派出一次投递；
- 一轮输出超过 200KB 的 Codex 会话、读不到的会话记录：确认判成忙或未知，不投；
- hook 比 `send-keys` 先返回：确认状态不倒退；
- 主 agent 已经 `Stop`、子 agent 还卡在授权框：确认不投；
- `codex queue` 调用超时：确认记「已写入未确认」，不重投；
- 有一条「已写入未确认」时，人手动另跑了一轮：确认阻挡不会被误解除，后面的消息继续排队；
- 送达确认比忙闲状态先刷新：确认不会紧接着再派一次。

### 第 5 步：App 里嵌终端

**做法**

- 成员详情里放一个终端控件，里面跑 `tmux attach -t <会话名>`。打开就能看、能打字；关掉面板只断开这一个 attach，agent 照常跑。
- **人工接管**：内嵌终端会让「人在打字、核心同时投递」更容易发生。面板上加一个「暂停自动投递 / 恢复」开关，暂停期间消息只排队不投；检测到有人在输入时，这一次投递取消补回车的资格。用户在外部终端 attach 时核心监控不到，只能靠第 3 步回车前的输入框复核兜底，文档和界面里写明这个边界。
- `status off`（隐藏状态栏）、`mouse on`（滚轮翻历史）只用 `set-option -t <会话>` 设在这几个会话上，**不碰用户的 tmux 全局配置**。
- 打开面板时才创建终端控件，关掉就释放；历史记录在 tmux 那边，SwiftTerm 自己只保留很少的回滚行数。
- 按项目规则，终端区域保持默认 I 形光标，面板里的按钮加 `.clickable()`。

**选型：SwiftTerm**。不选 libghostty：它用 GPU 渲染更快，但要引入 Zig 工具链，产物大好几 MB；这里只是一个面板显示一个终端，用不上。

**接入方式：先试编，再按实测选，不提前承诺体积**

- 固定 SwiftTerm 的某个 tag / commit。它的 `Package.swift` 里有构建插件和平台条件，**不能笼统地认为把全部源码交给 swiftc 就能编过**。
- 两种接法都试：(a) 挑出 macOS 需要的源码，和 App 一起交给 `swiftc` 编进同一个模块；(b) 在 `build.sh` 里用 SwiftPM 把 SwiftTerm 编成静态库再链接。两种都不需要新建 Xcode 工程。
- `-wmo`（整体优化）、`-Xlinker -dead_strip`（去掉没用到的代码）、`strip -x` 和接入方式**分开做对比**，按实测的 App 体积、打开终端后的内存、编译时间选。
- 保留 SwiftTerm 的 MIT 许可证。

**验收清单**

- 关掉面板只结束 attach 客户端，agent 照常跑；
- App 重启、核心重启后会话还在，能重新接上；
- 中文输入法、Unicode / emoji、多行粘贴；
- 改变面板大小时终端跟着变；用户同时在外部终端 attach 时，两个客户端的尺寸怎么处理；
- 滚轮回滚、Esc 键能正常传给 Claude；
- 关掉面板后没有遗留的 PTY 和进程。

### 第 6 步（KK 新提，待 pm 评审）：紧急消息——像 IM 里的 @，让对方停下来先看消息

**要解决的场景**：tester（或群主、KK）发现 coder 方向错了，不能等它这一轮做完，否则会一直错下去。

**定位：受控实验。** 「紧急排在最前」可以直接做；「按 Esc 打断」要先在真机上把下面的待实测项和验收场景都跑过，才承诺它是可靠的。在那之前界面上标为「实验功能」。

**两个级别**（不做数字权重，两级够用，判断简单）：

| 级别 | 怎么发 | 投递方式 |
|---|---|---|
| 普通（默认） | `kkAgent send ...` | 第 2 步：对方空闲了再合并投 |
| 紧急 | `kkAgent send --urgent ...`；界面输入框旁边加一个「紧急」开关 | 第一期：对方空闲后排在最前面合并送达。第二期：tmux 里的成员在干活时**先打断当前这一轮**，确认停下后再合并送进去，紧急的排在最前面 |

**打断流程**（首版只支持 tmux 里的 coder / tester）：

**紧急只是「可以打断」，不能绕过任何阻挡**：面板暂停、状态未知、授权框、已有的「已写入未确认」，这些阻挡对紧急消息同样有效。

1. 紧急消息入库后（状态 `pending`）立即唤醒这个会话的投递队列。
2. 看对方状态：
   - **空闲** → 不用打断，按第 3 步的普通流程立即投；
   - **主 agent 在干活** → 继续第 3 步；
   - **卡在授权框** → **不按 Esc**。Esc 在授权框上等于拒绝授权，这是人的决定。只通知群主和 KK「coder 在等授权，紧急消息会在授权处理后第一个送达」；
   - **未知** / **面板处于暂停状态** / **输入框里有人在打字** / **有「已写入未确认」** → 不打断，通知发送人：「对方暂时没法打断，已经排在最前面」。有人在操作时，以人为准。
3. **登记这次打断**：在这个会话的投递队列里原子认领，记下 interruptId、**目标回合的标识**、按键前会话记录的读取位置（offset）。登记期间核心不会往这个会话发起新的一轮。目标回合的标识按 agent 区分：
   - **Claude**：持久化的主 agent 开工序号（第几次主 agent 的 `UserPromptSubmit`）；
   - **Codex**（首版不装 hook）：会话记录里当前这一轮的 `turn_id`。
4. **按键前最后复查**：pane / launchId 没变、**目标回合还是同一个**（开工序号没变）、主 agent 仍在干活（只有后台子任务在跑时输入框是空闲的，不需要打断）、没有弹框、草稿或人工输入。任何一项变了就**不按**，下一轮也不顺延补按。然后 `send-keys Escape`，**只按一次**。
5. **确认已停下**，必须同时满足下面两条：
   - 会话记录里，按键前的 offset 之后、当前会话的主线上（**排除 `isSidechain: true` 和子 agent 的记录**），出现结构化的打断记录：`type: user`，内容是 `[Request interrupted by user]` 或 `[Request interrupted by user for tool use]`。要解析 JSON 结构，**不能全文搜文字**。如果这时**新的主回合已经开始**（开工序号变了），即使旧的打断记录现在才写进文件，也不能判定对方当前空闲；
   - Codex 只认**目标 `turn_id` 对应的** `turn_aborted` 或完成记录，offset 之后其他回合的 `turn_aborted` 不算；
   - 截屏组合判断：输入框可用、没有菜单、草稿或授权框、主 agent 已经不在忙。只看到 `❯` 或者画面不动，**不算**。
   - 也可能对方正好自然结束了这一轮。那就照常进入安全投递检查，但不能说成是我们打断的。
6. **10 秒内确认不了**：按「打断结果未知」处理。**紧急正文仍然保持 `pending`，不贴进去**，打断的阻挡继续保留，通知发送人；等目标回合确实结束、输入框确认可以写入，再走第 3 步的普通流程。超时后**不重复按 Esc**。注意「打断结果未知」和「已写入未确认」是两件事：前者只是 Esc 可能到了，正文根本还没写。
7. **合并投递**：
   - 紧急消息和普通消息**各自保持时间顺序**，紧急的一组排前面；每条标明来源和时间，并写明「紧急纠偏优先于和它冲突的旧指示」；
   - 打断期间又来了紧急消息：正文还没开始写入时，重新取一次要合并的消息；已经开始写入后，新来的归下一批，不改已有 attempt 的内容和摘要；
   - 开头的说明按实际情况写，只有**确认打断成功**时才说「已打断你当前的工作」。其他情况分别写：「你原本是空闲的」「你刚好结束了上一轮」「无法打断，这是排在最前面的消息」；
   - 确认打断成功时提醒对方：上一轮被中途打断了，先看完这些消息，再检查工作区里有没有改了一半的文件、跑了一半的命令，然后决定是否继续原来的工作。**打断主回合不代表子 agent、后台命令和外部副作用都停了**，所以不能因为 Esc 生效，就认定工作区不会再变。

**保证边界（要在文档和界面里写明）**：从截屏、启动 tmux 子进程到按键真正到达，这中间做不到原子操作。Esc 仍有可能正好落在旧一轮刚结束的空闲输入框、或者下一轮上，人在外部终端操作、或者 Claude CLI 自己的队列也会带来剩余的竞态。所以**不能严格保证「只停这一轮」**。要严格保证，需要回合级的协议（比如 Codex 的 `turn/interrupt`），而不是靠按 Esc。

**【待实测】**：本机 Claude 2.1.308 在 tmux 里被打断时，分别在「正在生成文字」「正在跑工具」「正好自然结束」三种时机下：会话记录写什么、什么时候写，会不会触发 hook。Orca 的样本来自 2.1.280 / 2.1.310 的其他接入方式，只能作参考，不能直接当结论。

**【实测结果】**（2026-11-12）
- 测试环境：单独的 tmux 会话 kktest-esc / kktest-codex，测试目录 `~/kkagent-esctest`，没碰正式会话。
- 版本：虚拟机里 coder 用的 Claude 2.1.322；宿主机 tester 用的 Codex（ChatGPT.app 自带，`--approve-for-me`）。

Claude 2.1.322：

| 按 Esc 的时机 | 会话记录 | hook | 输入框 |
|---|---|---|---|
| 正在输出文字 | 主线追加 `type:user`，content 数组里一段 text `[Request interrupted by user]`，和按键几乎同时写 | **不触发**（没有 Stop） | 空 |
| 正在思考、已经有 thinking 记录 | 同上 | 不触发 | 空 |
| 刚提交、还没有任何 assistant 记录（约 1 秒内） | **什么都不写**，只留下那条用户消息 | 不触发 | **原提示词被放回输入框**，多行的也一样 |
| 正在跑前台工具 | 先写一条 tool_result「The user doesn't want to proceed…」，再写 `[Request interrupted by user for tool use]` | 不触发（没有 PostToolUse，也没有 Stop） | 空 |
| 主回合已结束，只剩后台命令在跑 | 什么都不写 | 不触发 | 不变（按了没反应） |

- 后台命令跑完后，Claude 会自己开新的一轮：触发 UserPromptSubmit，prompt 以 `<task-notification>` 开头。开工序号会因此增加，不一定是有人发了消息。
- 放回输入框的多行提示词：Ctrl+U 只删当前行，要「Ctrl+U、退格」交替按好几次才能删干净。

Codex：

| 按 Esc 的时机 | 会话记录 | 输入框 |
|---|---|---|
| 正在跑命令 | `event_msg/turn_aborted`，带目标 `turn_id`，`reason: interrupted`；同时追加一条 `<turn_aborted>` 的 user 消息 | 空 |
| 刚提交（1 秒内） | 同上，已经有 task_started 和 turn_aborted | 空，不放回 |
| 空闲 | 什么都不写 | 底部提示「esc again to edit previous message」，**这时再按一次 Esc 会进入「编辑上一条消息」** |

- 打断后后台命令**还在跑**：界面显示「1 background terminal running」。
- Esc 后立刻输入的第一个字符可能被吞掉，被当成 Alt 组合键。

对实现的影响：
1. 打断后 Claude 不发 Stop，hook 状态会一直停在 working。确认打断后，核心要自己把 mainTurn 改成 idle，并且核对 revision。
2. 「刚提交就按 Esc」会把提示词放回输入框，而且会话记录里没有证据。所以按 Esc 的前提要加一条：目标回合在会话记录里已经有 assistant 记录（thinking、文字或工具调用都算）。这一轮才刚开始的话，先不打断，等下一次检查。
3. 「只按一次」对 Codex 是硬要求：空闲时多按一次就会进入编辑上一条消息。
4. 打断后不要马上贴文字；要等确认停下以后再走普通投递流程，这个间隔天然就有。

**「紧急」和「允许打断」是两回事**：

- 紧急消息**始终排在前面**；按不按 Esc 另外判断。
- **同一个目标回合只打断一次**：不管谁发（包括 KK 和群主），只要这一轮已经有一次打断正在进行、或者结果未知，后来的紧急消息只并进这一批纠偏消息，不再按 Esc。多人同时发紧急、或者连发，都只按一次。
- **跨回合的冷却**：成员之间（比如 tester → coder），同一个发送人对同一个目标 **5 分钟内只按一次 Esc**。超过时消息**仍然是紧急的**、照样排在前面，只是不打断，回执里说明。KK 和群主不受冷却限制。
- 打断记录按「会话 + launchId + 目标回合」**全局共享**，所有来源（成员、群主、KK）共用一条。认领和冷却计数都在会话队列里进行；**按 Esc 之前先落库，记成「可能已发出」**。核心崩溃或重启后，这条记录按「打断结果未知」恢复，不会对同一回合再按一次。
- 给成员的入群说明里写清楚：只在「对方继续做下去会白干、或者会造成破坏」时才用紧急；验收结论、进度同步一律用普通消息。

**其他投递方式（首版不支持打断，降级处理）**：

**（pm 评审定稿，2026-11-12）所有渠道都不开「立即投」的例外**：对方忙时紧急消息照样排队，空闲后排在最前面合并送达。暂停自动投递、授权框、人工接管、「已写入未确认」这些阻挡同样有效。原因：`codex queue` 和中转会话交出去后，对方也只是放进自己的队列，立即投并不能让它更早处理，反而会重新带回「忙时写入、确认不了」的问题。回执统一写「已标为紧急，满足投递条件后优先合并送达」，不承诺「第一个送达」，因为可能已经有一批正在写入，或者被暂停、未确认挡着。

| 成员 | 处理 | 原因 |
|---|---|---|
| 开着窗口的 Claude（经中转会话发送） | 不打断，排在最前，等空闲 | 那是 KK 自己正在用的窗口，不替人按 Esc |
| 桌面端 Codex（`codex queue`） | 不打断，排在最前，等空闲 | **接口已经确认**（官方文档 https://learn.chatgpt.com/docs/app-server ）：`turn/interrupt`（参数 threadId + turnId，返回 `{}` 后还要等对应的 `turn/completed`、`status=interrupted`）；还有更适合「先看纠偏意见」的 `turn/steer`（带 `expectedTurnId`，只往正在跑的那一轮追加输入，不新开一轮）。**待验证的是连接和所有权**：要连到真正持有这个活跃 thread 的 app-server；新起一个 app-server 去 resume 同一个 thread，控制不了桌面端或 tmux 里正在跑的实例。验证通过后，桌面端 Codex 可以用 `turn/steer` 做「不打断、直接塞进当前这一轮」，甚至可以给 tmux 里的 Codex 也换成这种回合级协议 |
| 后台续接的 Claude / Codex | 不抢占，等这一轮跑完；消息仍保留紧急标记，下一轮排在最前 | 要打断只能结束进程再续接，风险大，以后再说 |

**验证**：

- coder 干活中途 tester 发紧急消息：确认只按一次 Esc，确认停下后，紧急消息排第一、和排队消息一起送进去，coder 开始处理；
- coder 空闲时发紧急消息：不按 Esc，直接投；
- coder 卡在授权框时发紧急消息：不按 Esc，群里出现提示，授权处理后第一个送达；
- tester 5 分钟内连发两条紧急消息：第二条不按 Esc，但仍然排在最前、被优先处理，回执里有说明；
- KK、群主、tester 同时发紧急消息：只按一次 Esc，三条合进同一批纠偏消息；
- 打断的那一刻正好弹出授权框：不再继续，按授权框的规则处理；
- 按 Esc 时下一轮已经开始：最后复查发现回合标识变了，不按；
- 打断结果未知时核心重启：不对同一次打断再按一次；
- 面板暂停、或者 KK 正在输入框里打字时发紧急消息：不打断；
- 按了 Esc，但 10 秒内确认不了：不连按，紧急正文保持排队、不贴，等这一轮确实结束后再投；
- 按 Esc 前的最后复查时，对方正好结束了这一轮：不按，按普通流程投；
- 子 agent 被打断的记录（`isSidechain: true`）：不当成主回合已停下；
- 有一条「已写入未确认」时发紧急消息：不打断，排在最前面等着。

### 第 6 步第二期：详细设计（按 pm 2026-11-12 的 8 条意见修订；又按 pm 第二轮 7 条补齐，pm 已同意补齐后在测试核心实现）

范围：tmux 里的 Claude coder 和 Codex tester。其他渠道不打断，见上面的「其他投递方式」。

**1. 目标回合怎么认（pm 意见 4）**

- **Claude 用 promptId。** 实测：
  - hook 里 UserPromptSubmit 的 `prompt_id`，就是会话记录里这一轮所有 user 记录的 `promptId`；
  - Esc 写下的打断标记，带的也是被打断那一轮的 `promptId`。
  所以不需要持久化开工序号：
  - 认目标回合：hook 状态是 working，并且记着当前的 promptId（核心重启后状态是 unknown、promptId 为空，不按）。按之前，再到会话记录里核对：主线上最后一条「真正的提示词」的 promptId 就是它。
  - 「真正的提示词」：主线（`isSidechain != true`）、不是压缩摘要（`isCompactSummary`）的 user 记录，内容是文字、不含 tool_result，也不是打断标记。后台命令结束后 Claude 自己开的一轮（文字以 `<task-notification>` 开头）也算新的一轮。
  - 认打断：主线 user 记录，content 里 type=text 的那一段**整段等于**「[Request interrupted by user]」或「[Request interrupted by user for tool use]」，并且这条记录的 `promptId` 等于目标。正文里引用了这句话不算。
  - 认「这一轮已经有 assistant」：主线 assistant 记录顺着 parentUuid 往上找（跳过 attachment 等非对话记录），碰到的第一条 user 记录的 promptId 等于目标。只看文件位置不算。
  - 核心重启后要补认：直接按 promptId 到会话记录里找，不依赖内存。找不到目标 promptId 的记录（版本不同、缺字段）就当作证据不足，不按、不结算。
  - 按键还要求 Claude 版本是实测过的 2.1.322 或更新；版本未知不按。
- **Codex 用 turn_id。** 只有在 activeTurns 里**恰好一个**、非空的回合时才打断（跟踪结果必须可信：会话身份核对过、没有坏行、读到了完整的行尾）。只认这个 turn_id 的 `turn_aborted` 并且 `reason=interrupted`（算打断成功），或 `task_complete`（只算自然结束）；别的 reason 算结果未知。两种都还要求当前没有新的 active turn。`<turn_aborted>` 那条 user 文字不单独作证据。
- **启动标识：** Claude 用 launchId。Codex 没有 hook，用 tmux 的「pane_id + pane_pid」（就是 paneIdentity）。

**2. 打断记录表 interrupts（pm 意见 3、5）**

| 列 | 说明 |
|---|---|
| agent、vm、session_id | 实际会话，不用成员 ID |
| launch | 见上一节的启动标识 |
| target_turn | promptId / turn_id |
| member_id | 只用来关联来源 |
| sender_key | 稳定的发送者身份：成员发的取「agent\|vm\|sessionId」，用户发的取 `user`，群主发的取群主会话（不受跨群换成员行的影响） |
| exempt | 是否 KK 或群主发起（不受冷却限制） |
| state | 见下 |
| key_may_sent_at | 可能已经按过 Esc 的时间：改成 sent 时在同一条 UPDATE 里写上，之后不管结算成什么都不清 |
| alerted | 「结果未知」的告警发过没有（每条记录只发一次） |
| reason | 没按 / 结果未知的原因 |
| created_at、updated_at | |

（原来打算记会话记录的 offset 和文件身份，现在不用了：所有证据都按 promptId / turn_id 认，和读到文件的哪个位置无关，文件被截断、换段也不会认错。）

- 唯一键是（agent, vm, session_id, launch, target_turn）。同一回合不管谁发起，只能登记一次。
- state 的取值：
  - `registered`：已登记，还没按；
  - `aborted`：复查没通过，没按。这一回合以后也不再按，算保守结算；
  - `sent`：可能已经发出；
  - `confirmed`：确认打断成功；
  - `natural`：目标回合自己结束了；
  - `superseded`：已经开了新的一轮；
  - `unknown`：结果未知。
- 冷却：同一个 sender_key 对同一个实际会话，有 `key_may_sent_at` 在 5 分钟内的记录，就不再按，不管它现在是什么 state（sent → superseded 后照样算）。从没进过 sent 的 registered / aborted 不算冷却。exempt 只免冷却，同一回合的唯一键照样约束 KK 和群主，而且永久有效。
- 插入记录、查冷却时数据库出错，一律不按。
- 核心启动时，把 registered 改成 aborted，把 sent 改成 unknown，不会对同一回合再按一次。
- **未结算**的记录指 state 是 registered / sent / unknown。只要这个实际会话有未结算的记录，所有投递入口（Delivery.deliver 开头）和写前检查（writeBlocker）都不投；读库出错也不投。这条阻挡和 hook 状态无关：Codex 没有 hook，Claude 重启后变 unknown、靠截屏恢复空闲，都绕不过去。

**3. 流程**（在这个会话自己的串行队列里跑，也就是 Delivery.deliver 一开头的忙闲判断那里）

1. 判断为 busy，排队里有紧急消息，并且是 tmux 成员、没暂停、没有 blockingAttempt，才进入打断流程。
2. 看能不能打断：
   - Claude：hook 状态 working，授权等待全部为空，promptId 已知，会话记录里目标那一轮已经有 assistant 记录（避免「刚提交就按」把提示词放回输入框）。
   - Codex：activeTurns 恰好一个。
   - 有任何一项不满足，或者冷却中：不按，消息照样排在最前。
3. 插入 `registered`。
4. 最后复查：
   - paneIdentity 和 launch 没变，目标回合没变，仍在干活；
   - 没有弹框（复用 claudeScreen 里的弹框判断），输入框里没有字；
   - 重新读一次成员，确认没被暂停，也没有 blockingAttempt。
   没通过就改成 `aborted` 并记下原因，然后结束。
5. 改成 `sent`，然后 `send-keys Escape`，只按一次。改 `sent` 失败就不按，记录留在 registered，启动时会变成 aborted。
6. 10 秒内每 0.5 秒查一次：
   - Claude：会话记录里有目标 promptId 的打断标记，之后没有更新的真正提示词，并且截屏没有忙碌动画和弹框 → `confirmed`。
   - Claude 自然结束：目标回合最后一条主线 assistant 带 end_turn / stop_sequence、没有 tool_use（也就没有没做完的工具），之后没有更新的提示词 → `natural`。只是「没看到打断标记」不算。
   - Codex：见第 1 节的规则 → `confirmed` / `natural`。
   - 会话记录里出现了比目标更新的真正提示词（按文件里的先后顺序，Claude 包括 task-notification 开的一轮；Codex 是新的 active turn）→ `superseded`。内存里的 promptId 为空、或者和目标不同，都不能单独当作开了新的一轮。
   - 10 秒到了还认不出来 → `unknown`。
7. confirmed 或 natural 之后：
   - Claude：调用 `AgentStatusStore.markTurnEnded(memberId, launchId, promptId, revision) -> Bool`。在锁内核对 launch、promptId、revision 都没变，mainTurn 还是 working，并且授权等待全部为空，才把 mainTurn 改成 idle，不碰子 agent 的等待。返回值说明有没有改成；没改成（期间来了新事件）就重新取证，不能假设已经空闲。
   - Codex 不用改：track 已经反映了回合结束。
   - 然后回到普通流程：重新判断忙闲，重新取 pending、建投递批次。所有门禁都不跳过，包括暂停和输入框草稿。
   - 实测 Esc 之后紧接着输入的第一个字符可能被吞掉，所以确认打断后等 1 秒再粘贴。这 1 秒只是保护间隔，不是送达证据：粘贴后照样严格核对完整性、回车前核对原样，少字或状态不明就不回车、不补贴。
8. 10 秒内认不出来 → `unknown`：正文保持 pending，不贴，不再按。

**4. 结果未知之后（pm 意见 6）**

- 未结算的记录由第 2 节的阻挡挡住投递，不靠 hook 状态。
- 定时检查（poll）给每条未结算的记录排一次 settleInterrupt，**放进这个会话自己的串行队列**，和投递不会同时改状态；同一会话已经排上、还没执行的就不重复排。投递开头遇到未结算的记录，也先就地 settle 一次。
  - registered：能在队列里看到它，说明登记它的那次流程已经结束、却没能改成 sent 或 aborted（写库失败），也就一定没按过 → 改成 aborted。
  - sent / unknown：按第 3 节第 6 步同样的证据规则再认一次 → confirmed / natural / superseded；认到 confirmed / natural 后同样调用 markTurnEnded。
  - 写库失败的就留着，下一次定时检查再来，不用重启。
- 一直认不出来就保持原样，继续挡着。超过 2 分钟发一次告警（alerted 置 1，之后不再发），2 分钟只是提醒，不解除阻挡。
- 实测里「刚提交就按」的情况会话记录完全没有证据，这种情况只能人工处理。不会因为输入框空了就当成成功。
- **顺带的通用修复：** 人在终端里手动按 Esc，现在也会让 hook 一直停在 working，消息永远投不出去。定时检查对「hook 是 working、还有排队消息」的 tmux Claude 成员，用同一套证据解析：目标是内存里当前的 promptId，会话记录里它被打断或自然结束、之后没有更新的提示词，屏幕安全（没有忙碌动画和弹框）→ 调用 markTurnEnded（同样核对 launch、promptId、revision 和授权等待）。只恢复忙闲状态，不写 interrupts 记录，也不说是系统打断的。promptId 为空（重启后）不走这条，那时状态是 unknown，由原来的截屏 + 会话记录兜底。

**5. 输入框里残留的旧提示词（pm 意见 7）**

首版不自动清除。万一残留了，草稿门禁会挡住投递，再由第 4 节的告警提示人工处理。

**6. 给对方的开头说明**

只在批次里有紧急消息时才加，在合并说明或者单条正文的前面加一行，四种情况分开写：

| 情况 | 开头说明 |
|---|---|
| 确认打断成功 | 「你上一轮被中途打断了：先看完下面的消息，再检查工作区里有没有改了一半的文件，以及还在跑的后台命令，然后决定是否继续原来的工作。」 |
| 目标回合自己结束了 | 「你刚好结束了上一轮。」 |
| 本来就空闲 | 不加 |
| 没能打断 | 「没能打断你，这些消息排在最前面。」 |

**7. 通知发送人**

在群里记一条只给用户看的系统告警（from=system、to=user、kind=alert，不建投递记录，所以不会触发任何 agent），不另外唤醒发送人。成员发送人如果每次都收到通知，就会多跑一轮，还可能来回回复。回执里已经写了「满足投递条件后优先合并送达」。pm 已同意。

两种告警分开写，都标出目标成员、发起人、原因：
- 「没能打断，紧急消息仍排在最前」：每个目标回合只发一次（内存里按 会话 + 回合 去重）。冷却中不发，免得刷屏。
- 「按了 Esc 但结果没法确认，消息先不投，请到终端里看一下」：每条打断记录只发一次（alerted 列）。

**8. 第二期测试**（测试核心 7799 / ~/.kkagent-test）

- 测试隔离：测试核心带 `KKAGENT_CLI=~/.kkagent-test/bin/kkAgent-test` 启动，提示词里的命令都是这个包装的绝对路径（写死 7799，调用工作区新版 bin/kkAgent）。已真实回发验证：回复只落测试库，正式库 0 条。第二期测试用新建的会话。
- 原文「验证」列表里的每一条；
- pm 补充的场景：同一会话跨群多人同时发紧急、登记前后核心崩溃、重启后认回合、按键前遇到暂停 / 授权 / 自然结束、残留提示词被人工修改、结果未知后定时唤醒；
- 第二轮新增回归：sent → superseded 后冷却仍有效；重启后 promptId 为空不误判 superseded；Codex 有未结算记录时普通投递绕不过去；poll 和发送同时结算不冲突；打断后最快的粘贴路径首字符不丢（短消息、多行消息、连续两批）；
- 人手动按 Esc 后能自动恢复空闲；
- 保留：原有门禁全部生效、只按一次、不自动清草稿、开头说明提醒检查后台命令。

## 六、评审中的分歧和最终结论

| 议题 | coder 最初的想法 | pm 的意见 | 结论 |
|---|---|---|---|
| 进程代次 | tmux 会话名已经绑定成员，可以省掉 | 同名会话重建、pane 切换、进程退出都可能投错 | 采纳 pm：记 `pane_id` + `pane_pid` + launchId，粘贴前、回车前各核对一次 |
| `paste-buffer -p` | 一次写完 | 只在开启括号粘贴时加边界，并且分多次写 | 采纳 pm：回车前在屏幕上确认粘贴完整 |
| 怎么确认送达 | 开工计数增加 / 对方忙时有新输出 / 补回车 | 这些都证明不了是哪一条 | 采纳 pm，并加上 coder 提的投递编号：编号行完整解析 + 全文摘要比对；确认不了就记「已写入未确认」 |
| 虚拟机连核心 | 沿用 Relay 的网关办法 | 核心只监听 127.0.0.1，伪造 Host 头解决不了网络可达性 | coder 实测能连通，pm 接受；文档注明依赖 ubx 的行为 |
| 状态种类 | 4 种 | 6 种 | 4 种，pm 接受；「已退出」查 tmux，「启动中」由启动流程管 |
| 授权解除 | 任意 `PostToolUse`，后来改成任意 `PostToolBatch` | 必须同一主体、并且 `tool_calls` 里列出了在等的 `tool_use_id`（Orca 源码就是这么做的） | 采纳 pm |
| 子 agent 事件 | 全部过滤 | 普通事件过滤，授权框不能过滤 | 采纳 pm |
| 等授权放在哪 | 留在会话自己的队列里 | 可以接受，但要可取消、不挡 hook 和人手动操作 | 留在队列里，加上 pm 提的条件 |
| 核心重启后 | 状态 `unknown`，排队的消息照常补投 | 原来的授权框可能还在，而且不会再触发 hook | 采纳 pm：`unknown` 时先截屏读画面，排除不了弹框就暂停 |
| 等授权期间新来的消息 | 自然合并 | 现在的代码在 `send` 前就定死了要合并的消息 | 采纳 pm：授权解除后、写入前重新取一次 |
| SwiftTerm 接入 | 源码直接编进 App，体积更小 | 有构建插件和平台条件，先试编、不承诺体积 | 采纳 pm：两种接法都试，按实测选 |
| 对方忙时的消息 | 硬插进去，再想办法确认 | — | **KK 提出：忙就先存着，空闲再合并投。** coder 和 pm 都接受。它让「忙时插入确认不了」的情况大大减少，也避免了「等授权堵队列」，但「已写入未确认」的处理仍然保留 |
| 空闲判断 | 读一次 idle 就投；沿用 `isCodexBusy` | 要按会话原子认领；`isCodexBusy` 只看 200KB、默认空闲，不可靠 | 采纳 pm：复用按会话的串行队列做认领，有在途就不派新的；Codex 改成增量跟踪会话记录，判断不了就是「未知」，不投 |
| 检查点竞态 | 按顺序更新阶段 | hook 可能比回车先回来，阶段会倒退；重启后写入前的投递会被漏掉 | 采纳 pm：阶段只进不退；写入前的改回 pending 重新排队；规则同样适用于 `codex queue` 和中转会话 |
| 主 agent `Stop` | 清掉全部授权等待 | 子 agent 的授权可能还在 | 采纳 pm：只清主 agent 自己的 |
| 写入检查点 | `Tmux.paste` 一个函数做完 | 要分阶段落库，崩溃后能区分写没写过 | 采纳 pm：`pending → preparing → write_started → input_accepted → confirmed` |
| hook 可靠性 | 核心连不上就丢 | 参考 Orca 的 spool + 启动令牌 + 版本探测 | 采纳启动令牌、版本探测；spool 首版用读会话记录补齐代替 |
| 人工同时输入 | 只查粘贴前的草稿 | 用户可能在粘贴和回车之间打字 | 采纳 pm：回车前再查一次输入框；面板加「暂停自动投递」 |
| 验收结论晚到 | 没碰到过，不做 | 现有流程也可能发生 | 列为后续单独做 |

## 八、第 6 步之后要做的（2026-11-12 实际遇到的问题）

1. **同一个会话被起了两个进程**：普通群里开着窗口的 Claude 成员（比如 gic59 的 coder），窗口重启的那几秒，
   核心看状态文件以为「会话没打开」，就用 `claude -p --resume` 在后台续接投递。窗口随后又续接上，同一个会话出现两个进程，
   两边读同一份会话记录、同时改同一批文件（实际发生：22:16 后台进程 + 22:17 窗口进程，KK 手动 kill 掉后台那个）。
   要修：后台续接前确认这个会话确实没有活着的进程（不只看状态文件的那一瞬间），或者对开着窗口的会话不走后台续接。
2. **普通群的成员也能交给核心在 tmux 里托管**（KK 提的）：现在只有集群子群的 coder / tester 由核心在 tmux 里启动，
   能重开、能装 hook、能被紧急消息打断。普通群里拉进来的已有会话，核心不掌握进程。
   方案方向：成员详情里加「改成由核心在 tmux 里托管」，先确认原来的窗口进程已退出，再用同一个会话 ID 在 tmux 里 `--resume`
   并装 hook。这样也顺带解决上一条。先出方案给 pm 评审。
