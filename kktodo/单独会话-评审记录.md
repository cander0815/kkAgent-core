## 必须明确的正常路径

1. 列表不能只按 tmux 存不存在清理所有记录。POST 异步启动时，尤其 Codex exec bootstrap 阶段，tmux 本来就还不存在；GET 若立即删除，会删掉正在启动的会话。用最小的 starting/running/failed 启动状态区分：starting 留在列表，failed 按方案显示原因并允许清理，只有曾运行后确认 exit 的会话才退出运行列表。不要因此新增庞大的状态机。
2. 进程归属和群绑定必须显式存储，例如 members.standalone_id 或单独绑定关系。headless/tmux 相同不足以区分“群里创建”和“会话页创建”。原群内托管成员仍由群拥有，移出/解散继续关闭；solo 绑定成员只解除绑定。状态键使用可区分的 member/solo 身份，不能让两个表的整数 ID 混用。
3. solo 销毁或 exit 后，群里的绑定成员要停止接收投递，取消尚未开始的群消息，已有未确认记录按现有规则结算或保留，不能被宣称送达。最重要的是禁止投递定时器和成员面板重新打开逻辑调用 ensureTmuxSession 自动重建该 solo；当前群托管路径正会在 tmux 不在时重建，与用户定义“exit 就结束”冲突。可保留明确的“已退出”成员行或移除成员，但不能只删 solo 行然后丢失归属信息。
4. 从群里解绑时撤销该群待投消息和调度，但不能调用会杀进程的 delivery.cancel 去终止正在共用的 solo 终端。解绑后 hook 的 solo 令牌/主状态继续有效；重新绑进普通群，映射到当前成员，不能重新 prepareLaunch、换令牌或新开 bootstrap。只有完成启动的 solo 才可选入群。
5. hook 和恢复统一按持久的托管归属定位。现有 member hook 路径保留兼容；solo hook 使用独立身份，绑定前后不换来源。onIdle/onPermission、确认证据及 interrupt 里原先按 memberId 查状态的调用点一并通过映射读取同一份状态；不要维护两份可相互覆盖的副本。解绑、重新绑定和核心重启都沿用这一规则。
6. 单独 Codex 的最小初始化明确要求立即结束、不轮询等待；未绑定时不发群入群说明。绑定时再发普通群说明、沿用忙时排队及草稿/暂停/授权/未确认门禁，不得因为“拉入”而往用户正在输入的终端直接粘贴。

## 验证补充

- POST 返回后立即 GET，Codex bootstrap 尚无 tmux 时条目不丢；失败能看到并销毁。
- solo 正在工作或输入框有草稿时拉入群，复用原 pane/pid，入群消息排队。
- 入群、解绑、再入群以及核心重启后，hook 工作状态、授权等待和紧急消息仍取同一份状态。
- 绑定群里还有 pending 消息时主动 exit/销毁，刷新和 poll 都不重建进程、不续接后台副本。
- 普通群“群里新建”的原有成员移出/解散仍关闭，与 solo 成员只解绑的行为分别回归。

启动和终端实现尽量复用，不要求为未发生的数据库、网络等低概率异常另建防御系统。先在测试核心 7799、新测试会话验证；本轮只方案评审，未修改业务代码、批准合并或部署。

## kk#2090：实现复核

### P1：销毁启动中的 Codex 未终止 bootstrap 进程

`runSoloCodexOpening` 直接创建 Process，没有按 solo ID 登记到可取消进程集合，也没有登记到 terminateAll 使用的 allProcesses。destroySolo 只更新状态、kill tmux；此时 Codex exec 尚在运行，tmux 本来就还没有。

隔离使用一个输出 thread.started 后执行 sleep 的假 Codex CLI：创建 solo，确认 bootstrap 启动，调用实际 destroySolo 后数据库变为 ended，但进程仍存活；随后调用实际 terminateAll，进程仍存活。最后由驱动显式终止并确认回收，仅处理自建假 CLI。

要求：按 solo ID 登记启动进程，并纳入核心退出时的进程回收；销毁 starting 会话时取消 bootstrap，不能只隐藏条目或等默认超时。启动路径同步遵守销毁状态，避免销毁后继续进入 tmux 启动。无需新增通用任务系统。

### P2：启动中重启后 starting 永久悬空

startSolo 只由创建时的后台闭包驱动；核心重启后没有恢复该闭包。当前 checkSolos 只处理 running 且 tmux 消失的记录，不会处理启动遗留的 starting。

隔离登记 starting，重新打开数据库、构造新 DeliveryQueue 并执行实际 restore/checkSolos，记录仍为 starting。与当前 main 启动路径核对，没有后续收尾逻辑。用户在几秒到一分钟的初始化阶段重启核心即可遇到，列表会永久显示正在启动。

要求：启动时收尾上次遗留的 starting。已有 tmux 可正向确认就绪时接管；无法确认则显示明确的启动中断/失败及可销毁重建操作。首版不要求自动续启或复杂重试，但不能永远 starting。与 P1 一起确保旧 bootstrap 不遗留成副本。

### 独立通过和范围

- starting 尚无 tmux 时列表保留。
- solo 状态与普通成员状态分别保存；绑定成员通过 StatusOwner 指向同一 solo 状态和原 tmux。
- 解绑后不 kill tmux，solo 的 working 状态保留。
- tmux 已结束的 solo 不能通过 ensureTmuxSession 自动重建。
- 当前完整 Core/Shared 快照编译及 git diff 检查通过。

### P1 剩余：退出时取消 bootstrap 后仍继续启动

驱动第二个场景输出 thread.started 后等待，调用 terminateAll 停掉 bootstrap。readDataToEndOfFile 随即结束，runSoloCodexOpening 仍从已收到的 thread.started 返回 ID；startSolo 只检查持久状态 starting，未检查 isStopping，因此继续调用 Tmux.start 并把记录改成 running。结果中可见“核心退出，停止投递进程”之后出现“单独会话已启动”。

要求：取消后的启动线程停止推进。bootstrap 返回后及 tmux 创建前检查核心正在退出；创建后也要处理退出已开始的情况，不让退出中的新启动越过门禁。保留原来已运行 tmux 随核心重启存活的行为，不需要新建调度系统。新增回归：thread.started 已输出但 bootstrap 尚未完成时 terminateAll，确认该启动不再进入 tmux 创建；重启后按已有恢复策略收尾。
