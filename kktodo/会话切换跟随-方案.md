# 会话里 /clear、/resume 之后，kkAgent 跟着换到新会话

日期：2026-11-13
来源：KK 在单独会话 solo-10 里先 `/resume`、又 `/clear`，kkAgent 还记着启动时的会话 ID。KK 确认群成员一起改。
状态：KK 定了 3.4 用 B。已在测试核心 7799 上开发并真机验证（结果见第七节），待评审；替换正式环境等 KK 说。

## 一 要解决什么

kkAgent 在 tmux 里启动 Claude 时，会把会话 ID 写进数据库（`solo_sessions.session_id` / `members.session_id`），之后**一直认这个 ID**。用户在终端里敲 `/clear`（开一个新会话）或 `/resume <ID>`（换到另一个会话）之后，Claude 进程还是同一个，会话 ID 却变了，kkAgent 不知道。

solo-10 的实际情况：

| 位置 | 会话 ID |
| --- | --- |
| 数据库里记的 | `8080e748`（启动时的 `--session-id`），这个文件从来没生成过 |
| 实际经历 | 先 `/resume` 到 `52d32189`，后来 `/clear` 成 `faf4e068` |

带来的问题（单独会话和 tmux 里的群成员都一样）：

1. **状态全部失效**：每个 hook 事件都带着当前的 `session_id`，核心只认登记时的 ID，对不上就丢掉（`AgentStatus.swift` 的 `record`）。所以执行中 / 需要授权 / 本轮结束、小红点、系统通知都不再有。群成员不会变成「空闲」，排队的消息也就不会被唤醒投递。
2. **核心会认为会话不在了**：核心靠 `~/.claude/sessions/<pid>.json` 里的 `sessionId` 判断会话活着没有（`Transcript.claudeLiveStatus`），实测这个文件在 `/clear` 后会换成新 ID。按旧 ID 查不到，给群成员的通知会被当成「会话没开着」跳过（`Delivery.enqueueNotice`）。
3. **投递确认对不上**：确认消息送达要比对这个会话最近提交的内容（`recentPrompts(owner:sessionId:)`），ID 不一致就拿不到。
4. **重开就接错**：核心重启、tmux 被重新拉起时，按数据库里的旧 ID `--resume`，接回的是旧会话，不是用户正在用的那个。
5. **显示错**：会话名、会话内容都按旧 ID 去找。

## 二 实测结论（Claude Code 2.1.323，虚拟机，tmux 里真机跑）

用一个临时 tmux 会话，装上只记录事件的 hook，依次做了 启动 → `/clear` → `/rename` → `/clear` → `/resume <ID>`，事件顺序如下：

| 操作 | 事件 | session_id | 字段 |
| --- | --- | --- | --- |
| 启动（`--session-id A`） | SessionStart | A | `source: "startup"` |
| `/clear` | SessionEnd | A（旧） | `reason: "clear"` |
|  | SessionStart | B（新） | `source: "clear"` |
| `/clear` | SessionEnd → SessionStart | B → C | `reason: "clear"` / `source: "clear"` |
| `/resume B` | SessionEnd | C（旧） | `reason: "resume"` |
|  | SessionStart | B（换到的） | `source: "resume"` |

另外确认了：

- SessionStart 的数据里有 `session_id`、`cwd`、`transcript_path`、`source`，**没有** `prompt_id`、`agent_id`。
- 同一个进程的 `~/.claude/sessions/<pid>.json`，`sessionId` 在 `/clear` 后立刻变成新 ID。
- `/clear` 之后新会话的记录文件**不会马上生成**，要等第一条消息或改名才落盘。

结论：**SessionStart 事件就足够了**，它直接告诉我们这个进程现在用的是哪个会话。SessionEnd 不需要。

## 三 方案

### 3.1 多装一个 SessionStart hook

`AgentStatusStore.writeHookFiles` 的事件列表里加上 `SessionStart`。hook 脚本不用改，它本来就把事件原样转给核心，带着启动令牌（launchId）。

### 3.2 核心收到 SessionStart：换成新会话

在 `AgentStatusStore.record` 里，**放在「session_id 对得上才认」这一关之前**处理 SessionStart：

1. 只认启动令牌对得上的（launchId 对就说明是我们起的那个 tmux 进程，不会被别的会话冒充）。
2. 新 ID 和登记的一样（启动、`/compact`）→ 什么都不做。
3. 新 ID 不一样 → 换：
   - **冲突检查**：新 ID 已经被另一个运行中的单独会话、或别的群成员用着（比如 `/resume` 到了别人的会话），就不换，记一条日志。这和现有「更换成员的会话」接口的检查一致：一个会话不能同时被两处托管。
   - **内存**：登记里的 sessionId 换成新的；最近提交记录、等授权记录、当前这一轮的 prompt_id 清空；状态记成「空闲」（`/clear`、`/resume` 只能在输入框里敲，说明这时没有在跑的一轮），然后调用 onIdle，唤醒排队的投递。
   - **数据库**（新方法 `Repository.followSession`）：
     - 单独会话：改 `solo_sessions` 这一行的 `session_id`、`cwd`。
     - 所有 `agent`、`vm`、`session_id` 都和旧值一样的成员行，一起改 `session_id`、`cwd`。这一条同时覆盖了三种情况：tmux 里的群成员自己、绑着这个单独会话的群成员、被复制进各个子群的群主行（它们照抄的是同一个会话 ID）。
     - `cwd` 取事件里带的 `cwd`。
   - 记一条日志：「solo/12 会话从 A 换成 B（clear）」。
4. 之后这个进程的事件带的都是新 ID，原有逻辑照常工作。核心重启后从数据库恢复登记，用的也是新 ID。重新拉起 tmux 时，新会话的文件已经生成就用 `--resume`，还没生成（刚 `/clear` 还没说过话）就用 `--session-id` 新建同一个 ID。这是 `Delivery.tmuxLaunch` 现有的判断，不用改。

为什么不复用现有的 `changeSession`（`POST /api/members/:id/session`）：

- 它是给用户手动把成员换到另一个已有会话用的，要求新会话文件已经存在（`/clear` 后还没有），并且不允许改后台会话（headless）。
- 而这里是同一个 tmux 进程自己换了会话，tmux 和进程都没变，集群的 coder 在 tmux 里 `/clear` 也应该跟着换。

所以单独写一个更窄的「跟随」，只改会话 ID 和 cwd。

### 3.3 换的那一刻还没处理完的事

- **还没确认的投递**（attempts 表按会话 ID 记）：`/clear` 只能在空闲时敲，这时一般没有进行中的投递。万一有，按现有「成员换了会话」的规则处理：旧会话的投递不拿新会话的记录确认（`recentPrompts` 的注释里已经写明），最后按现有的超时规则算作没确认、重投。不额外处理。
- **还没结算的 Esc 打断**（interrupts 表按会话 ID 记）：同上，打断只针对正在跑的一轮，`/clear` 时不会有。不额外处理。

### 3.4 群成员 `/clear` 之后忘了自己在群里（需要 KK 定）

`/clear` 后是一个全新的会话，入群说明（群 ID、自己叫什么、怎么用 `kkAgent send` 回消息）都不在上下文里了。别人发来的消息照样能送到，但它不知道该怎么回。`/resume` 到一个没进过群的会话也一样。

可选做法：

| 做法 | 怎么做 | 代价 |
| --- | --- | --- |
| A 不管 | 只换 ID，用户自己负责 | 群成员 `/clear` 后基本没法协作 |
| B 跟着 SessionStart 补进上下文（推荐） | Claude 会把 SessionStart hook 的输出加进上下文。核心对 SessionStart 的回复带上这个成员的入群说明（每个所在的群一段），hook 脚本对 SessionStart 把回复打印出来 | 不额外跑一轮，`/clear` 完立刻就知道自己在群里。要改 hook 脚本（现在把回复丢掉了），并且要实测确认输出真的进了上下文 |
| C 排队一条入群说明 | 换完后给它投递一条入群说明 | 会触发它跑一轮回复，用户刚 `/clear` 可能正要自己交代事情，会被打断 |

单独会话没进群的，B 和 C 都不发东西。

**KK 选了 B。** 补进去的内容：开头一句说明「刚换了会话，下面重新给出入群说明」，后面每个所在的群一段：
- 集群主群用群主版说明（`Prompts.ownerIntro`）；
- 子群里复制来的群主行跳过，主群那段已经说清楚了；
- 其他（普通群成员、子群的 coder / tester）用普通入群说明（`Prompts.intro`）。子群 coder / tester 原来的开工说明里带着任务内容，这里不重发。`/clear` 本来就是用户主动清掉上下文，任务要用户自己重新交代。

### 3.5 已经在跑的会话

现在已经开着的会话没装 SessionStart，要**下次重新拉起后才生效**。实测过：Claude 运行中把 `--settings` 文件改成带 SessionStart，再 `/clear`，收不到这个事件，说明不会自动重新加载。界面上不做提示，靠自然重启过渡。

## 四 不做的和原因

- **Codex**：没有装 hook，要靠扫会话记录才能发现 `/new` 换了线程，代价大。等 KK 实际用到再说。
- **不在 kkAgent tmux 里的成员**（在用户自己终端里开的会话，用中转或 `claude -p --resume` 投递）：没装 kkAgent 的 hook，收不到 SessionStart。这种会话本来就由用户自己管，换会话可以用现有的「更换会话」。
- **SessionEnd**：SessionStart 已经够了，不处理。
- **界面**：不用改。App 拿到的会话 ID 和名字都来自核心，跟着就对了。

## 六 验证（测试核心 7799，真机跑，不拿模拟当验证）

1. 单独会话：新建 → 终端里 `/clear` → 查数据库 `solo_sessions.session_id` 已是新 ID；让它跑一轮，「会话」页显示执行中 → 本轮已结束，有通知。
2. 单独会话：`/resume <另一个已有会话>` → 数据库换成那个 ID；`/resume` 到一个正被别的单独会话用着的 ID → 不换，日志里有说明。
3. tmux 群成员：在它的终端里 `/clear` → 数据库成员行换成新 ID → 另一个成员用 `kkAgent send` 给它发消息 → 消息送进新会话并确认送达（查 deliveries / attempts 状态）。（选 B）它能用 `kkAgent send` 正确回复。
4. 集群群主是 tmux 成员时 `/clear` → 主群和各子群里的群主行都换成新 ID；子群 coder 汇报能送到。
5. 换完后重启测试核心 → 状态登记用的是新 ID，hook 事件照常被认；杀掉 tmux 后重新打开 → 接回的是新会话。
6. `/clear` 后不说话直接重启 tmux → 用 `--session-id` 新建同一个 ID，不报错。
